# Wex и реактивность

Разрабатывая приложения, разработчик рано или поздно столкнётся с комплексностью. 
Сперва внезапно появился, скажем, экран продажника. Теперь экран кассира. 
А приложение тем временем одно и тоже, просто усложняется логика вывода.
Напару с усложнением логики вывода, происходит взрыв условных операций под капотом. Что это?
Это когда у вас в ваших if условиях появляются ещё одни ветки if, в них else, и так далее.
Поддерживать становиться невозможно, читать тоже, расширять - ужас, по другому - никак.
Решая проблему "по другому - никак" нам в индустрию постучалась реактивность. Что это? Обьясняю.

# Реактивность

State (стэйт, состояние) - это базовое понятие реактивности и всех реактивных движков. 
Стейт это состояние приложения, его снимок, набор переменных в памяти. Но зачем? 
Что нам мешает создать обычные переменные через `let x = 5`? Ничего. Но мы что-то теряем. Что? Обьясняю. 

## Декларативность 

Когда мы обьявляем переменную вот так нагло и открыто, мы ручаемся что будем её использовать.
Ведь зачем-то она нам нужна, верно? А зачем? Мы говорили про глобальный стейт приложения и реактивность.
Стейт это по сути набор переменных. Таких как `let x = 5`, просто хранящихся определенынм образом 
в определенном месте. Но в отличии от такого обьявления переменной, где мы полно и цельно берём
за неё ответственность, для стейта ответственность не нужна. Он сам механизм-реализатор ответственности.
Так что же он делает? Сейчас расскажу. 

## Стейт 

Возьмем, на примере, Wex. Мою разработку реактивную как аналог и прямой конкурент React.
```js 
$('#app')
  .state({ title: 'Default Title' })
  .mount()
```
Что здесь происходит? Если идти по шагам, то алгоритм следующий:
1. Выбери мне элемент с айдишником app 
2. Проинициализируй ему стейт со свойством title
3. Смонтируйся в выбранный элемент 

Всё. Ничего сложного, и на странице при этом ничего не произошло. Тогда же зачем этот стейт нужен,
если страница осталась всё такой же? Всё дело в шаблонизаторе и в механизме обработки стейта. 
Сейчас расскажу.

## Шаблонизатор

Каждый фронтентд фреймворк имеет собственный шаблонизатор и виртуальный DOM. Виртуальный DOM 
это по сути сборка всего HTML на странице и создание его виртуальной копии в памяти, грубо 
говоря Вы создаёте переменную `x` куда помещаете ASM-дерево всех узлов вашего HTML-документа 
для будущего развёртывания. Например: `x = ['div', 'p', 'span']`. Но зачем? Для шаблонизатора. 

```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>
```
Смотрите внимательно, что здесь происходит. Мы используем тэг template, который буквально 
не отображается в браузере. Он нужен специально, чтобы наш движок создал виртуальный DOM 
из этого участка кода, самостоятельно не удаляя его из вывода браузера, ведь его итак там 
нет благодаря тэгу template. 

Второе, это присвоение этому темплейту уникального айдишника. Если Вы вспомните предыдущий
код, то именно благодаря айдишнику происходит первичная зацепка и выборка элемента: `$('#app')`.

И, наконец, третье - подозрительно непонятный `{{ title }}` в коде. Что это? 
Ради этого, собственно говоря, всё и затевалось. 

## Реактивный шаблонизатор (или реакткивный DOM)

Реактивность это просто слово означающее наибыстрейший. В данном контексте - наибыстрейшее 
обновление данных. Что будет после запуска нашей страницы с кодом? Попробуйте сами!
```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>
<script>
    $('#app')
      .state({ title: 'Default Title' })
      .mount()
</script>
```
Если не хотите ручками играться у себя в браузере, то вывод будет следующим:
```
Default Title
```
Да, вот так просто. Обычный текст на экране без премудростей. Тогда зачем это всё? 

Всё ради реактивности. А именно: когда мы обновим наш стейт, молниеносно перерендериться
весь наш компонент и обновит все значения свои, где он на этот стейт и ссылался.
То есть, как только в коде мы поменяем значение `title`, молниеносно на экране браузера
мы получим его новое значение. Ну не круто ли? Сейчас просто комплесно сравним 
старый императивный подход к разработке и новый декларативный подход. Всё познается
в сравнении. 

# Сравнение

```html 
<template id="app">
    <div class="num">{{ number }}</div>
</template>

<script>
    $('#app')
      .state({ number: 0 })
      .on('click', '.num', state => {
        state.number = state.number + 1;
      })
      .mount()
</script>
```
Этот код вывод на страницу символ 0, и каждый раз когда ты будешь на него кликать, 
он будет увеличиваться ровно на еденицу. Теперь посмотрим тот же код на jQuery.
```html 
<div class="num">0</div>

<script>
    let num = 0;
    
    $('.num').on('click', function() {
        num++;
        $('.num').innerText = num;
    });
</script>
```
Чувствуете разницу, как код становится комплекснее и грязнее? Когда мы целиком берём 
ответственность за переменную? Сейчас это называется императивный подход - это подход,
когда мы контролируем каждый чих, вместо доверия. Декларативность же, напротив, делает 
всё сама, главное скажи что делать. 

А теперь представьте что стейт широкий у приложения? Что в нём не один маленький `let num = 0`, 
а реально тонна, как и полагается более-менее сложному приложению? Представили? Ну как? 
Нравится картина? Это старая боль JS разработчиков. Ровно за этим фреймворки и придумывались.
Поддерживаемость такого подхода нулевая или околонулевая, в сравнении с декларативностью.

В реактивных движках мы следим лишь за стейтом. Мы выносим за скобки весь перерендер, 
и оставляем его на волю движка доверяя ему как чёрному ящику, что он сделает всё в лучшем 
виде. А это мы ещё не переходили к созданию динамического HTML'a - очень частая задача 
в среде браузерного JS. Когда наш шаблонизатор умеет итерировать и создавать динамику 
прямо в HTML'e `w-for`, то мы попадаем буквально в сказку! 

# Сравнение 2 

Wex-реактивная библиотека. Декларативный подход.
```html 
<template id="app">
    <div class="list" w-for="listItem in list">
        <ul>
            <li>{{ listItem }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({ list: ['privet', 'kak', 'dela'] })
      .mount()
</script>
```
jQuery-нереактивная библиотека. Императивный подход.
```html 
<div class="list">
    <ul></ul>
</div>

<script>
    const list = ['privet', 'kak', 'dela'];

    list.forEach(item => {
        $('ul').append('<li>' + item + '</li>');
    });
</script>
```

О, нет! HTML прямо в JS... Уже пахнет вонючим кодом... Но да, так и есть. Действительно: 
это полное нарушение MVC-паттерна, вывод смешался с логикой. Так не должно быть. 
Мы по факту организовали шаблонизатор в коде и это плохо. Но отставим красоту и паттерны.
Взгляните чистым свежим взглядом: какой подход Вам более понятен, близок и по душе?

Если второй, ничего страшного. Раздутый JS с кусками HTML внутри это не страшно,
можно поддерживать. Да, тяжело. Но можно. Если же Вам понравился первый вариант,
то значит реактивность это то, что Вам нужно!

## Сравнение 3. TODO-Приложение.

TODO-Приложения, казалось бы, достаточно легки в реализации, но это отнюдь не так.
Это всегда комплексные и масштабные приложения с витиеватой логикой. 
Но давайте попробуем такое комплексное приложение реализовать на Wex!

```html 
<div>
    <template id="app">
        <div>
            <input w-bind="newTodo" placeholder="Новая задача..." />
            <button w-on="click:addTodo">Добавить</button>

            <div w-for="todo,index in todos traceby todo.id">
                <span>{{ todo.text }}</span>
                <button w-on="click:remove(todo.id)">Удалить</button>
            </div>
        </div>
    </template>
</div>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>

<script>
    $('#app')
        .state(() => ({
            newTodo: '',
            todos: [],
        }))

        // Кнопка добавить
        .fn('addTodo', function (state) {
            // Наш инупт забинжен через w-bind="newTodo", данные сразу тут будут
            let inputText = state.newTodo.trim()

            let newTodo = {
                id: Date.now(), // даём уникальный ид
                text: inputText // заносим сюда текст из инпута
            }

            state.todos.push(newTodo) // пушим наш новый туду в стейт
            state.newTodo = '' // очищаем инпут, ведь он забинжен и очистится вместе со стейтом
        })

        // Кнопка удалить
        .fn('remove', function (state, id) {
            
            // формируем список новых тудушек, покаместь пустой
            let newTodos = []

            // пробегаемся по текущим тудушкам чтобы вычислить все айдишники
            for (let i = 0; i < state.todos.length; i++) {

                // создаём новую локальную переменную с текущей тудушкой
                let todo = state.todos[i]

                // проверяем что текущая тудушка из нашей for-крутилки 
                // не равна айдишнику удаляемой тудушки
                if (todo.id !== id) {

                    // все остальные тудушки кроме текущей удаляемой добавляем в новый список
                    newTodos.push(todo)
                }
            }

            // реактивно обновляем стейт новыми тудушками без той что мы удалили
            state.todos = newTodos
        })

        .mount()
</script>
```
