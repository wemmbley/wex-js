# Серверные компоненты и современные парадигмы рендеринга

Прежде чем разбирать архитектуру — нужно понять картину целиком. 
Откуда вообще берётся HTML который видит пользователь, и почему это важно.

## Откуда приходит HTML

Существует три принципиально разных ответа на этот вопрос.

### CSR — Client Side Rendering. 
Сервер отдаёт почти пустую страницу и большой JavaScript-файл. 
Браузер скачивает JS, выполняет его, и только тогда на экране появляется контент. 
Именно так работают React, Vue и Angular по умолчанию. 
Пользователь первые секунды смотрит на белый экран или спиннер. 
Поисковый робот видит то же самое — пустоту — и с трудом индексирует контент.

### SSR — Server Side Rendering. 
Сервер каждый раз при запросе генерирует готовый HTML 
и отдаёт его браузеру. Пользователь видит контент мгновенно. Поисковик получает 
полноценную страницу. PHP с Blade, Ruby on Rails, Django — классические примеры SSR. 
Это не новомодная идея, а то как веб работал изначально.

### SSG — Static Site Generation. 
HTML генерируется один раз заранее — при сборке проекта 
— и раздаётся всем пользователям как статический файл. Максимально быстро, 
но не подходит для динамических данных. Например, кэширование Blade в Laravel.

```
CSR:  Запрос → пустой HTML + JS → браузер рисует → контент
SSR:  Запрос → сервер думает → готовый HTML → контент
SSG:  Сборка → готовый HTML → Запрос → контент (мгновенно)
```

## В чём проблема чистого CSR

Next.js, Nuxt, SvelteKit — все эти фреймворки появились именно потому что 
CSR оказался неудобен для реального бизнеса. Пришлось изобретать 
«серверные компоненты» поверх изначально клиентских фреймворков. 

Получилось сложно: в Next.js нужно явно писать 'use client' чтобы объяснить 
фреймворку что этот компонент интерактивный, а тот — нет. Два режима, 
два способа мышления, много нюансов.

PHP-first подход переворачивает это с головы на ноги. 
По умолчанию всё серверное — SEO из коробки, быстрая загрузка, никакого белого экрана. 
А туда где нужна интерактивность — аккуратно добавляется WEX.

## Серверный компонент vs клиентский компонент

Серверный компонент — это Blade-шаблон, Twig, Jinja или любой другой шаблонизатор. 
Он живёт на сервере, видит базу данных, знает кто авторизован, имеет доступ 
к переменным окружения. Его результат — готовый HTML, который летит в браузер.

Клиентский компонент — это WEX-вью. Он живёт в браузере, реагирует на действия 
пользователя, обновляет интерфейс без перезагрузки страницы.

| Описание                     | Серверный (Blade)   | Клиентский (WEX)        |
|-------------------------------|-------------------|-------------------------|
| Где выполняется               | PHP-сервер         | Браузер пользователя    |
| Видит БД                      | ✓ напрямую         | ✗ только через API      |
| Виден поисковикам             | ✓ сразу            | зависит от данных       |
| Реагирует на клики            | ✗                  | ✓                       |
| Обновляется без перезагрузки  | ✗                  | ✓                       |
| Хранит стейт                  | ✗                  | ✓                       |

Они не конкуренты — они партнёры. Каждый делает то, что умеет лучше.

## Базовая архитектура — просто

В простейшем случае всё выглядит так: Blade рисует страницу, 
WEX добавляет жизнь туда где она нужна.

```bladehtml
{{-- resources/views/products/index.blade.php --}}

<h1>Каталог товаров</h1>

{{-- Это серверный HTML — поисковик его прочитает --}}
@foreach($products as $product)
    <div class="product-card">
        <h2>{{ $product->name }}</h2>
        <p>{{ $product->price }} ₽</p>
    </div>
@endforeach

{{-- А это уже WEX — только для интерактивного фильтра --}}
<template id="filter">
    <input w-bind="query" placeholder="Поиск по каталогу">
    <div w-if="query.length > 0">
        Ищем: {{ query }}
    </div>
</template>

<script>
    $('#filter').state({ query: '' }).mount()
</script>
```

Товары отрендерил PHP — их увидит Google. Поиск с живой фильтрацией 
добавил WEX — пользователь получил интерактивность.

## Масштабная архитектура

Когда WEX-компонент становится сложным — он начинает обрастать кодом. 
Всё в одном `<script>` становится нечитаемо. Именно здесь Blade раскрывается 
как инструмент организации JavaScript-кода.

Посмотрите на пример следующей структуры моего компонента Obsidian:
```
obsidian/
├── bootstrap.blade.php     ← создаёт глобальный объект window.Obsidian
├── state.blade.php         ← описывает начальный стейт
├── factory.blade.php       ← фабрика: собирает вью из частей
├── hooks/
│   ├── mount.blade.php     ← логика при монтировании
│   └── update.blade.php    ← логика при обновлении
└── actions/
    └── fullscreen.blade.php ← конкретные действия
```
Каждый файл — один маленький <script> с одной ответственностью. 
Blade просто склеивает их в нужном порядке через @include. 
Никакого webpack, никакого npm — только PHP и браузер.

### Фабрика собирает готовый компонент из кусков:

```js 
// factory.blade.php
window.Obsidian.init = function(selector, overrides) {
    return $(selector)
        .state(Obsidian.State(overrides))     // ← из state.blade.php
        .on('$mount',  Obsidian.Hooks.mount)  // ← из hooks/mount.blade.php
        .on('$update', Obsidian.Hooks.update) // ← из hooks/update.blade.php
        .on('click', '.toggle-fullscreen-btn', Obsidian.Hooks.toggleFullscreen)
        .mount();
};
```

А использовать его на любой странице теперь одной строкой:
```bladehtml
{{-- любая страница где нужен редактор --}}
<template id="editor-1"></template>

<script>
    Obsidian.init('#editor-1')
</script>
```

Хотите второй редактор с другим начальным контентом — просто передаёте overrides:
```bladehtml
Obsidian.init('#editor-2', {
    storage: { content: 'Начальный текст...' }
})
```

## Когда совмещать, а когда нет

Хорошее правило: если данные нужны поисковику или должны появиться 
мгновенно — это работа сервера. Если данные появляются в ответ 
на действие пользователя — это работа WEX.

Отдавайте серверу:
- каталоги, статьи, карточки товаров — всё что индексируется
- данные из базы которые не меняются без действия пользователя
- авторизацию и права доступа
- начальное состояние страницы

Отдавайте WEX:
- формы и их валидацию
- фильтры, сортировки, поиск
- модальные окна, табы, аккордеоны
- всё что меняется без перезагрузки страницы
- счётчики, корзины, лайки

## Реальные кейсы:
Интернет-магазин — каталог рендерит PHP (SEO), но фильтр по цене и 
добавление в корзину делает WEX (интерактивность).

Блог — статьи отдаёт сервер (поисковик читает полный текст), но форма 
комментариев с live-preview работает через WEX.

Админ-панель — здесь SEO не нужен вовсе, зато нужна богатая интерактивность. 
Blade даёт структуру и авторизацию, WEX берёт на себя весь UI.

## Главная идея

В мире React и Next.js SSR — это дополнение которое нужно специально 
подключать и настраивать. В мире PHP — SSR это просто то как всё 
работает по умолчанию, и WEX добавляется точечно туда где нужна интерактивность.

Это не компромисс и не костыль — это честное разделение труда. 
Сервер делает то в чём он силён, браузер делает то в чём силён он. 
Пользователь получает быструю страницу, поисковик — полноценный контент, 
разработчик — простую и понятную архитектуру без магии.

```
Пример с Obsidian показывает что даже сложный интерактивный компонент 
— редактор с fullscreen-режимом, подсчётом слов и сохранением в localStorage 
— можно построить на этой связке аккуратно и читаемо. Blade организует файлы, 
WEX управляет стейтом, каждый занимается своим делом.
```
