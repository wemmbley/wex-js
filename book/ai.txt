# Wex и реактивность

Разрабатывая приложения, разработчик рано или поздно столкнётся с комплексностью. 
Сперва внезапно появился, скажем, экран продажника. Теперь экран кассира. 
А приложение тем временем одно и тоже, просто усложняется логика вывода.
Напару с усложнением логики вывода, происходит взрыв условных операций под капотом. Что это?
Это когда у вас в ваших if условиях появляются ещё одни ветки if, в них else, и так далее.
Поддерживать становиться невозможно, читать тоже, расширять - ужас, по другому - никак.
Решая проблему "по другому - никак" нам в индустрию постучалась реактивность. Что это? Обьясняю.

# Реактивность

State (стэйт, состояние) - это базовое понятие реактивности и всех реактивных движков. 
Стейт это состояние приложения, его снимок, набор переменных в памяти. Но зачем? 
Что нам мешает создать обычные переменные через `let x = 5`? Ничего. Но мы что-то теряем. Что? Обьясняю. 

## Декларативность 

Когда мы обьявляем переменную вот так нагло и открыто, мы ручаемся что будем её использовать.
Ведь зачем-то она нам нужна, верно? А зачем? Мы говорили про глобальный стейт приложения и реактивность.
Стейт это по сути набор переменных. Таких как `let x = 5`, просто хранящихся определенынм образом 
в определенном месте. Но в отличии от такого обьявления переменной, где мы полно и цельно берём
за неё ответственность, для стейта ответственность не нужна. Он сам механизм-реализатор ответственности.
Так что же он делает? Сейчас расскажу. 

## Стейт 

Возьмем, на примере, Wex. Мою разработку реактивную как аналог и прямой конкурент React.
```js 
$('#app')
  .state({ title: 'Default Title' })
  .mount()
```
Что здесь происходит? Если идти по шагам, то алгоритм следующий:
1. Выбери мне элемент с айдишником app 
2. Проинициализируй ему стейт со свойством title
3. Смонтируйся в выбранный элемент 

Всё. Ничего сложного, и на странице при этом ничего не произошло. Тогда же зачем этот стейт нужен,
если страница осталась всё такой же? Всё дело в шаблонизаторе и в механизме обработки стейта. 
Сейчас расскажу.

## Шаблонизатор

Каждый фронтентд фреймворк имеет собственный шаблонизатор и виртуальный DOM. Виртуальный DOM 
это по сути сборка всего HTML на странице и создание его виртуальной копии в памяти, грубо 
говоря Вы создаёте переменную `x` куда помещаете ASM-дерево всех узлов вашего HTML-документа 
для будущего развёртывания. Например: `x = ['div', 'p', 'span']`. Но зачем? Для шаблонизатора. 

```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>
```
Смотрите внимательно, что здесь происходит. Мы используем тэг template, который буквально 
не отображается в браузере. Он нужен специально, чтобы наш движок создал виртуальный DOM 
из этого участка кода, самостоятельно не удаляя его из вывода браузера, ведь его итак там 
нет благодаря тэгу template. 

Второе, это присвоение этому темплейту уникального айдишника. Если Вы вспомните предыдущий
код, то именно благодаря айдишнику происходит первичная зацепка и выборка элемента: `$('#app')`.

И, наконец, третье - подозрительно непонятный `{{ title }}` в коде. Что это? 
Ради этого, собственно говоря, всё и затевалось. 

## Реактивный шаблонизатор (или реакткивный DOM)

Реактивность это просто слово означающее наибыстрейший. В данном контексте - наибыстрейшее 
обновление данных. Что будет после запуска нашей страницы с кодом? Попробуйте сами!
```html 
<template id="app">
  <div class="title">{{ title }}</div>
</template>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>
<script>
    $('#app')
      .state({ title: 'Default Title' })
      .mount()
</script>
```
Если не хотите ручками играться у себя в браузере, то вывод будет следующим:
```
Default Title
```
Да, вот так просто. Обычный текст на экране без премудростей. Тогда зачем это всё? 

Всё ради реактивности. А именно: когда мы обновим наш стейт, молниеносно перерендериться
весь наш компонент и обновит все значения свои, где он на этот стейт и ссылался.
То есть, как только в коде мы поменяем значение `title`, молниеносно на экране браузера
мы получим его новое значение. Ну не круто ли? Сейчас просто комплесно сравним 
старый императивный подход к разработке и новый декларативный подход. Всё познается
в сравнении. 

# Сравнение

```html 
<template id="app">
    <div class="num">{{ number }}</div>
</template>

<script>
    $('#app')
      .state({ number: 0 })
      .on('click', '.num', state => {
        state.number = state.number + 1;
      })
      .mount()
</script>
```
Этот код вывод на страницу символ 0, и каждый раз когда ты будешь на него кликать, 
он будет увеличиваться ровно на еденицу. Теперь посмотрим тот же код на jQuery.
```html 
<div class="num">0</div>

<script>
    let num = 0;
    
    $('.num').on('click', function() {
        num++;
        $('.num').innerText = num;
    });
</script>
```
Чувствуете разницу, как код становится комплекснее и грязнее? Когда мы целиком берём 
ответственность за переменную? Сейчас это называется императивный подход - это подход,
когда мы контролируем каждый чих, вместо доверия. Декларативность же, напротив, делает 
всё сама, главное скажи что делать. 

А теперь представьте что стейт широкий у приложения? Что в нём не один маленький `let num = 0`, 
а реально тонна, как и полагается более-менее сложному приложению? Представили? Ну как? 
Нравится картина? Это старая боль JS разработчиков. Ровно за этим фреймворки и придумывались.
Поддерживаемость такого подхода нулевая или околонулевая, в сравнении с декларативностью.

В реактивных движках мы следим лишь за стейтом. Мы выносим за скобки весь перерендер, 
и оставляем его на волю движка доверяя ему как чёрному ящику, что он сделает всё в лучшем 
виде. А это мы ещё не переходили к созданию динамического HTML'a - очень частая задача 
в среде браузерного JS. Когда наш шаблонизатор умеет итерировать и создавать динамику 
прямо в HTML'e `w-for`, то мы попадаем буквально в сказку! 

# Сравнение 2 

Wex-реактивная библиотека. Декларативный подход.
```html 
<template id="app">
    <div class="list" w-for="listItem in list">
        <ul>
            <li>{{ listItem }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({ list: ['privet', 'kak', 'dela'] })
      .mount()
</script>
```
jQuery-нереактивная библиотека. Императивный подход.
```html 
<div class="list">
    <ul></ul>
</div>

<script>
    const list = ['privet', 'kak', 'dela'];

    list.forEach(item => {
        $('ul').append('<li>' + item + '</li>');
    });
</script>
```

О, нет! HTML прямо в JS... Уже пахнет вонючим кодом... Но да, так и есть. Действительно: 
это полное нарушение MVC-паттерна, вывод смешался с логикой. Так не должно быть. 
Мы по факту организовали шаблонизатор в коде и это плохо. Но отставим красоту и паттерны.
Взгляните чистым свежим взглядом: какой подход Вам более понятен, близок и по душе?

Если второй, ничего страшного. Раздутый JS с кусками HTML внутри это не страшно,
можно поддерживать. Да, тяжело. Но можно. Если же Вам понравился первый вариант,
то значит реактивность это то, что Вам нужно!

## Сравнение 3. TODO-Приложение.

TODO-Приложения, казалось бы, достаточно легки в реализации, но это отнюдь не так.
Это всегда комплексные и масштабные приложения с витиеватой логикой. 
Но давайте попробуем такое комплексное приложение реализовать на Wex!

```html 
<div>
    <template id="app">
        <div>
            <input w-bind="newTodo" placeholder="Новая задача..." />
            <button w-on="click:addTodo">Добавить</button>

            <div w-for="todo,index in todos traceby todo.id">
                <span>{{ todo.text }}</span>
                <button w-on="click:remove(todo.id)">Удалить</button>
            </div>
        </div>
    </template>
</div>

<script src="https://unpkg.com/jquery/dist/jquery.min.js"></script>
<script src="https://cdn.jsdelivr.net/gh/wemmbley/wex-js@master/dist/wex.min.js"></script>

<script>
    $('#app')
        .state(() => ({
            newTodo: '',
            todos: [],
        }))

        // Кнопка добавить
        .fn('addTodo', function (state) {
            // Наш инупт забинжен через w-bind="newTodo", данные сразу тут будут
            let inputText = state.newTodo.trim()

            let newTodo = {
                id: Date.now(), // даём уникальный ид
                text: inputText // заносим сюда текст из инпута
            }

            state.todos.push(newTodo) // пушим наш новый туду в стейт
            state.newTodo = '' // очищаем инпут, ведь он забинжен и очистится вместе со стейтом
        })

        // Кнопка удалить
        .fn('remove', function (state, id) {
            
            // формируем список новых тудушек, покаместь пустой
            let newTodos = []

            // пробегаемся по текущим тудушкам чтобы вычислить все айдишники
            for (let i = 0; i < state.todos.length; i++) {

                // создаём новую локальную переменную с текущей тудушкой
                let todo = state.todos[i]

                // проверяем что текущая тудушка из нашей for-крутилки 
                // не равна айдишнику удаляемой тудушки
                if (todo.id !== id) {

                    // все остальные тудушки кроме текущей удаляемой добавляем в новый список
                    newTodos.push(todo)
                }
            }

            // реактивно обновляем стейт новыми тудушками без той что мы удалили
            state.todos = newTodos
        })

        .mount()
</script>
```

# Двойное связывание (он же биндинг)

Чтобы нам не приходилось вручную писать алгоритм связи вводимых пользователем данных
и нашего стейта, было придумано понятие биндинга. Двусторонний биндинг, это по сути
зависимость стейта от вводимых данных. То, что написано в инпуте, моментально 
летит в стейт, и то, что изменилось в стейте, моментально меняется в инпуте. 
По сути так и строится вся реактивность. Рассмотрим на примере. 

```html 
<template id="app">
    <input w-bind="mytext">
    <span>Вы ввели: {{ mytext }}</span>
</template>

<script>
    $('#app')
      .state({ mytext: '' })
      .mount()
</script>
```

Таким простым способом мы сделали реактивный вывод вводимых данных.

## Поддерживаемые элементы для биндинга

`w-bind` работает на трёх типах элементов — `input`, `textarea` и `select`. 
Принцип одинаков для всех: пользователь что-то выбирает или вводит — стейт обновляется мгновенно.

```html 
<template id="app">
    <input w-bind="name" placeholder="Имя">
    <textarea w-bind="comment" placeholder="Комментарий"></textarea>
    <select w-bind="city">
        <option value="kh">Харьков-Царь</option>
        <option value="odessa">Одесса-мама</option>
        <option value="kiev">Киев-Русь</option>
    </select>

    <p>Имя: {{ name }}</p>
    <p>Комментарий: {{ comment }}</p>
    <p>Город: {{ city }}</p>
</template>

<script>
    $('#app')
      .state({ name: '', comment: '', city: 'kh' })
      .mount()
</script>
```
⚠ `w-bind` — это именно двусторонняя связь. Если вы поменяете значение в стейте программно, 
инпут тоже обновится. Это отличает его от `w-value`, который работает только в одну сторону 
— из стейта в элемент.

## Предзаполненный стейт
Начальное значение в стейте автоматически попадёт в поле при монтировании. 
Удобно для форм редактирования:
```html 
<template id="app">
    <input w-bind="username">
    <span>Привет, {{ username }}!</span>
</template>

<script>
    $('#app')
      .state({ username: 'Рустам' })
      .mount()
</script>
```
Пользователь сразу увидит своё имя в поле и сможет его отредактировать — стейт 
подхватит изменения на лету. 

# Условный вывод

Иногда бывают ситуации необходимости вывести-скрыть определенный блок со страницы.
Имея под собой реактивность и стейт, а так же мощный шаблонизатор, это становится
рядовой и тривиальной задачей. Усложним предыдущий пример.

```html 
<template id="app">
    <input w-bind="mytext">
    <span>Вы ввели: {{ mytext }}</span>
    <div w-if="mytext === 'фильм'">
        Вы ввели слово фильм! Тайный блок открыт!
    </div>
</template>

<script>
    $('#app')
      .state({ mytext: '' })
      .mount()
</script>
```

## Как работает w-if

`w-if` принимает любое JavaScript-выражение, которое приводится к `true` или `false`. 
Если выражение истинно — элемент рендерится в DOM, если нет — его там просто нет.
Это важное отличие от простого CSS-скрытия: элемент не просто становится невидимым, 
он физически отсутствует в дереве до тех пор, пока условие не выполнится.

```html 
<template id="app">
    <input w-bind="age" placeholder="Введите возраст">

    <div w-if="age >= 18">
        Добро пожаловать!
    </div>
    <div w-if="age > 0 && age < 18">
        Доступ только с 18 лет.
    </div>
</template>

<script>
    $('#app')
      .state({ age: '' })
      .mount()
</script>
```

## Переключение по булевому флагу
Самый частый сценарий — показать или скрыть блок по кнопке. 
Для этого в стейте держим флаг и меняем его через `on`:
```html 
<template id="app">
    <button class="toggle-btn">Показать детали</button>

    <div w-if="!!isOpen">
        Здесь скрытые детали, которые видны только после нажатия.
    </div>
</template>

<script>
    $('#app')
      .state({ isOpen: false })
      .on('click', '.toggle-btn', state => {
          state.isOpen = !state.isOpen;
      })
      .mount()
</script>
```
`!!isOpen` — двойное отрицание явно приводит значение к булевому типу. 
Хорошая привычка, особенно когда в стейте могут оказаться `null` или `undefined`.

## w-if внутри w-for

`w-if` и `w-for` отлично уживаются вместе — можно фильтровать элементы списка прямо в шаблоне:
```html 
<template id="app">
    <div w-for="item,index in products traceby item.id">
        <div w-if="!!item.inStock">
            {{ index + 1 }}. {{ item.name }} — в наличии
        </div>
    </div>
</template>

<script>
    $('#app')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   inStock: true  },
              { id: 2, name: 'Молоко', inStock: false },
              { id: 3, name: 'Сыр',    inStock: true  },
          ]
      })
      .mount()
</script>
```
Молоко не попадёт в DOM вовсе — только товары с `inStock: true`.

# Цикличный вывод

Порой нам надо динамически просмотреть стейт и вывести всё его состояние. Для этого 
в шаблоне реализована директива `w-for`, которая базово выглядит следующим образом:

```html 
<template id="app">
    <div class="list" w-for="listItem in list">
        <ul>
            <li>{{ listItem }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({ list: ['privet', 'kak', 'dela'] })
      .mount()
</script>
```

Здесь происходит перебор значений из массива стейта и вывод их по заданному шаблону.

## Индекс элемента

Если помимо значения нужен порядковый номер элемента, достаточно добавить второй аргумент 
— без пробела между ними:

```html 
<template id="app">
    <div class="list" w-for="listItem,index in list">
        <ul>
            <li>{{ index + 1 }}. {{ listItem }}</li>
        </ul>
    </div>
</template>
```
⚠ Важно: `listItem,index` — без пробела внутри. `,index` необязателен.

## Traceby — отслеживание уникальных элементов

Когда список меняется (элементы добавляются, удаляются, перемещаются), 
WEX по умолчанию перерисовывает весь блок целиком. Это работает, но неэффективно — 
особенно если список большой или элементы содержат сложную вёрстку.

Traceby говорит фреймворку: «смотри не на позицию элемента, а на конкретное поле — 
и перерисовывай только то, что реально изменилось».

```html 
<template id="app">
    <div class="list" w-for="item,index in users traceby item.id">
        <ul>
            <li>{{ index + 1 }}. {{ item.name }}</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({
          users: [
              { id: 1, name: 'Алиса' },
              { id: 2, name: 'Боб' },
              { id: 3, name: 'Вера' },
          ]
      })
      .mount()
</script>
```
Теперь если в массив добавится новый пользователь или один из них удалится — 
WEX не будет трогать узлы с уже знакомыми id. Это экономит ресурсы и исключает 
визуальные мигания при обновлении.

## Вывод обьектов
На практике `w-for` чаще всего работает не с плоскими строками, а с массивом объектов. 
Обращаться к полям можно напрямую через точку:
```html 
<template id="app">
    <div class="list" w-for="product,index in products traceby product.id">
        <ul>
            <li>{{ index + 1 }}. {{ product.name }} — {{ product.price }} ₽</li>
        </ul>
    </div>
</template>

<script>
    $('#app')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   price: 45  },
              { id: 2, name: 'Молоко', price: 89  },
              { id: 3, name: 'Сыр',    price: 320 },
          ]
      })
      .mount()
</script>
```

# Атрибуты-директивы

Помимо биндинга и условного вывода, WEX предоставляет набор специальных атрибутов, 
которые управляют поведением и внешним видом элементов прямо из стейта. 
Все они работают по одному принципу: значение в стейте меняется — атрибут на элементе 
меняется автоматически. Не нужно руками лезть в DOM, писать `$('.btn').addClass(...) `
или `$('img').attr('src', ...)` — шаблон САМ за всем следит.

## w-value — значение поля из стейта

Устанавливает значение `input`, `textarea` или `select` односторонне — только из стейта в элемент. 
В отличие от `w-bind`, изменения пользователя обратно в стейт не летят.
Используется когда нужно просто отобразить данные в поле, не слушая ввод:
```html 
<template id="app">
    <input w-value="username" placeholder="Имя пользователя">
    <textarea w-value="bio"></textarea>
    <select w-value="role">
        <option value="admin">Администратор</option>
        <option value="user">Пользователь</option>
    </select>
</template>

<script>
    $('#app')
      .state({
          username: 'Алиса',
          bio: 'Люблю котиков и кофе.',
          role: 'admin'
      })
      .mount()
</script>
```

`w-value` — читает стейт и всё, ничего более. `w-bind` — читает и перезаписывает его обратно. 
Другими словами `w-value` иммутабельный ридер, в том время как `w-bind` мутабельный ридер-райтер.
Если нужна форма редактирования, берите `w-bind`. Если просто показать данные в поле — `w-value`.

## w-class — динамические классы

Позволяет добавлять и убирать CSS-классы в зависимости от условий стейта. 
По сути тот же `w-if`, только работает с классами. 
Принимает объект, где ключ — имя класса, значение — условие:
```html 
<template id="app">
    <button class="toggle-btn">Переключить</button>

    <div w-class="{ 'active': !!isActive, 'highlighted': score > 50 }">
        Этот блок меняет классы
    </div>

    <p>Очки: {{ score }}</p>
</template>

<script>
    $('#app')
      .state({ isActive: false, score: 75 })
      .on('click', '.toggle-btn', state => {
          state.isActive = !state.isActive;
      })
      .mount()
</script>
```

Класс active появится когда `isActive` станет `true`. Класс `highlighted` уже висит 
с самого начала — потому что score равен 75. Обычный атрибут `class` и `w-class`
прекрасно уживаются на одном элементе.

## w-disabled — блокировка элементов

Делает элемент недоступным для взаимодействия. Работает на `input`, `textarea`, `select` и `button`:
```html 
<template id="app">
    <input w-bind="email" placeholder="Email">
    <button class="submit-btn" w-disabled="!isValid">Отправить</button>
</template>

<script>
    $('#app')
      .state({ email: '', isValid: false })
      .on('input', 'input', state => {
          state.isValid = state.email.includes('@');
      })
      .mount()
</script>
```

Кнопка заблокирована до тех пор, пока пользователь не введёт корректный email. 
Никакого ручного `$('button').prop('disabled', true)` — стейт сам всем управляет.

## w-checked — чекбоксы и радиокнопки

Управляет состоянием checked у `input[type=checkbox]` и `input[type=radio]`:
```html 
<template id="app">
    <label>
        <input type="checkbox" w-checked="!!agree">
        Я согласен с условиями
    </label>

    <input type="radio" name="size" value="s" w-checked="size === 's'"> S
    <input type="radio" name="size" value="m" w-checked="size === 'm'"> M
    <input type="radio" name="size" value="l" w-checked="size === 'l'"> L

    <p w-if="!!agree">Размер выбран: {{ size }}</p>
</template>

<script>
    $('#app')
      .state({ agree: false, size: 'm' })
      .mount()
</script>
```

Для чекбокса — просто булевое значение. Для радиокнопок — сравнение 
текущего значения стейта с `value` конкретной кнопки. При монтировании `M` будет 
отмечен автоматически, потому что `size: 'm'`.

## w-selected — выбранный option

Управляет атрибутом `selected` у отдельных option внутри `select`. 
Удобно когда список опций генерируется через `w-for`:
```html 
<template id="app">
    <select>
        <option
            w-for="city in cities traceby city.id"
            w-selected="chosenId === city.id"
            w-value="city.id">
            {{ city.name }}
        </option>
    </select>

    <p>Выбран город с id: {{ chosenId }}</p>
</template>

<script>
    $('#app')
      .state({
          chosenId: 2,
          cities: [
              { id: 1, name: 'Париж' },
              { id: 2, name: 'Харьков' },
              { id: 3, name: 'Техас' },
          ]
      })
      .mount()
</script>
```

Харьков будет выбран по умолчанию — потому что `chosenId: 2` совпадает с его `id`.

## w-src — источник изображения

Устанавливает атрибут `src` у картинки из стейта. Всегда используйте `w-src` вместо 
обычного `src` когда путь к изображению динамический — иначе браузер попытается 
загрузить `src="{{avatarUrl}}"` буквально:

```html 
<template id="app">
    <div w-for="user in users traceby user.id">
        <img w-src="user.avatar" alt="Аватар">
        <span>{{ user.name }}</span>
    </div>
</template>

<script>
    $('#app')
      .state({
          users: [
              { id: 1, name: 'Алиса', avatar: '/images/alice.jpg' },
              { id: 2, name: 'Боб',   avatar: '/images/bob.jpg'   },
          ]
      })
      .mount()
</script>
```

## w-id — уникальный идентификатор узла

Присваивает виртуальному узлу стабильный внутренний идентификатор. 
WEX использует его при диффинге — чтобы точно понять какой DOM-элемент обновить, 
а какой не трогать:

```html 
<template id="app">
    <div w-for="msg in messages traceby msg.id">
        <div w-id="msg-{{msg.id}}" w-class="{ 'unread': !msg.read }">
            {{ msg.text }}
        </div>
    </div>
</template>

<script>
    $('#app')
      .state({
          messages: [
              { id: 1, text: 'Привет!',    read: true  },
              { id: 2, text: 'Как дела?',  read: false },
              { id: 3, text: 'Ответишь?',  read: false },
          ]
      })
      .mount()
</script>
```
`w-id` особенно полезен когда несколько однотипных блоков существуют рядом 
и нужно исключить путаницу при перерисовке. Значение должно быть стабильным 
и уникальным в пределах одного шаблона.

# Обработка событий через шаблон

До этого момента мы вешали все обработчики событий в скрипте через `.on()`. 
Это основной и рекомендуемый способ в WEX. Но иногда удобнее объявить связь 
прямо в шаблоне — особенно когда элементов много и каждый должен вызывать 
свою функцию. Для этого существует директива `w-on`.

Главное что нужно понять: `w-on` не живёт без `fn`. Директива в шаблоне — это 
только половина, она лишь указывает имя функции. Саму функцию нужно 
зарегистрировать в скрипте через `.fn()`.

```html 
<template id="app">
    <input w-bind="message" placeholder="Введите сообщение">
    <button w-on="click:handleSubmit">Отправить</button>
    <p w-if="!!sent">Сообщение отправлено: {{ message }}</p>
</template>

<script>
    $('#app')
      .state({ message: '', sent: false })
      .fn('handleSubmit', state => function(e) {
          state.sent = true;
      })
      .mount()
</script>
```

Синтаксис `w-on="событие:имяФункции"` — событие это любое DOM-событие: 
`click`, `input`, `change`, `submit`, `keyup` и так далее.

## Несколько событий на разных элементах

Когда в шаблоне много интерактивных элементов, `w-on` позволяет держать связи 
прямо в разметке — не нужно угадывать по селектору в скрипте что к чему относится:

```html 
<template id="app">
    <input w-bind="query" w-on="input:onSearch" placeholder="Поиск...">
    <button w-on="click:onClear">Очистить</button>
    <button w-on="click:onSubmit">Найти</button>

    <p>Результат: {{ result }}</p>
</template>

<script>
    $('#app')
      .state({ query: '', result: '' })
      .fn('onSearch', state => function(e) {
          state.result = state.query.length > 0
              ? `Ищем: "${state.query}"`
              : '';
      })
      .fn('onClear', state => function(e) {
          state.query  = '';
          state.result = '';
      })
      .fn('onSubmit', state => function(e) {
          state.result = `Запрос отправлен: "${state.query}"`;
      })
      .mount()
</script>
```

## w-on внутри w-for

Особенно `w-on` раскрывается в списках — когда каждый элемент должен реагировать 
на событие со своими данными. Через `.fn()` в `state` уже доступен весь контекст:

```html 
<template id="app">
    <div w-for="item,index in cart traceby item.id">
        <span>{{ item.name }} — {{ item.qty }} шт.</span>
        <button w-on="click:onRemove">Удалить</button>
    </div>
    <p>Итого позиций: {{ cart.length }}</p>
</template>

<script>
    $('#app')
      .state({
          cart: [
              { id: 1, name: 'Хлеб',   qty: 2 },
              { id: 2, name: 'Молоко', qty: 1 },
              { id: 3, name: 'Сыр',    qty: 3 },
          ]
      })
      .fn('onRemove', state => function(e) {
          const btn   = $(this);
          const index = btn.closest('[w-for]').index();
          state.cart.splice(index, 1);
          this.update();
      })
      .mount()
</script>
```

Когда вы меняете массив методами вроде `splice`, `push` или `sort` — 
WEX не всегда замечает изменение автоматически. В таких случаях 
вызывайте `this.update()` вручную внутри функции — `this` внутри обработчика это сам `view`.

## Разница между w-on и .on()

Описание различия |   `w-on` в шаблоне  |   `.on()` в скрипте
------------------+---------------------+------------------------
Где описана связь | прямо на элементе   | в скрипте по селектору
Нужен ли `fn`     | обязательно         | нет, логика inline
Удобно когда      | много разных кнопок | одно событие на группу
Читаемость        | видно в шаблоне     | видно в скрипте

Оба подхода рабочие. Можно смешивать в одном приложении — никаких конфликтов нет.

# Статические узлы

Реактивность — это удобно, но не бесплатно. При каждом изменении стейта 
WEX проходит по шаблону, сравнивает виртуальное дерево с реальным DOM 
и обновляет то, что изменилось. Для большинства элементов это быстро, 
но если в шаблоне есть блоки которые никогда не зависят от стейта — 
зачем тратить на них время при каждом перерендере?

Именно для этого существует `w-static`. Один раз отрисовал — и больше не трогаю.

```html 
<template id="app">
    <div w-static>
        <h1>Добро пожаловать в наш магазин</h1>
        <p>Работаем с 2010 года. Доставка по всей стране.</p>
    </div>

    <p>Товаров в корзине: {{ cartCount }}</p>
    <button class="add-btn">Добавить</button>
</template>

<script>
    $('#app')
      .state({ cartCount: 0 })
      .on('click', '.add-btn', state => {
          state.cartCount++;
      })
      .mount()
</script>
```

Заголовок и описание отрисуются один раз при монтировании. 
Сколько бы раз `cartCount` ни менялся — WEX не будет заходить в этот блок вообще.

## Когда w-static особенно полезен

Статичные шапки, футеры, иконки, рекламные баннеры, длинные текстовые блоки — 
всё что не меняется в зависимости от данных. Особенно заметный эффект даёт 
разметка со сложной структурой или большим количеством вложенных тегов:

```html 
<template id="app">
    <header w-static>
        <nav>
            <a href="/">Главная</a>
            <a href="/catalog">Каталог</a>
            <a href="/about">О нас</a>
            <a href="/contacts">Контакты</a>
        </nav>
    </header>

    <main>
        <p>Привет, {{ username }}!</p>
        <button class="logout-btn">Выйти</button>
    </main>

    <footer w-static>
        <p>© 2024 Все права защищены</p>
    </footer>
</template>

<script>
    $('#app')
      .state({ username: 'Алиса' })
      .on('click', '.logout-btn', state => {
          state.username = 'Гость';
      })
      .mount()
</script>
```

header и footer заморожены навсегда. При клике на кнопку обновится только 
`username` внутри main — WEX даже не посмотрит в сторону статичных блоков.

⚠ `w-static` — необратимо. После первого рендера блок отвязывается 
от реактивной системы полностью. Не используйте его там где 
данные могут измениться — даже если сейчас кажется что не изменятся.

# Как WEX работает под капотом

Когда вы пишете `.state({...}).mount()` — снаружи всё выглядит как магия. 
Данные меняются, страница обновляется сама. Но внутри происходит чёткая 
последовательность шагов, понимание которой помогает писать более осознанный 
код и объясняет почему одни вещи работают именно так, а не иначе.

## Реактивный стейт — прокси над объектом

Первое что делает WEX при монтировании — оборачивает ваш объект состояния в `Proxy`. 
Это стандартный JavaScript-механизм перехвата операций над объектом.
```html 
$('#app')
  .state({ count: 0 }) // ← этот объект станет Proxy
  .mount()
```

Каждый раз когда вы делаете `state.count = 5` внутри обработчика — `Proxy` перехватывает 
это присвоение и вызывает `nextTick`. Сам `nextTick` — это `throttle-функция` с задержкой 
16 миллисекунд (одного кадра). Это значит что если вы изменили стейт десять раз подряд 
в одном обработчике — перерисовка произойдёт один раз, по истечении 16мс. 
Никаких лишних перерисовок.

```js 
.on('click', '.btn', state => {
    state.a = 1  // ← Proxy поймал
    state.b = 2  // ← Proxy поймал
    state.c = 3  // ← Proxy поймал
    // перерисовка будет одна, через ~16мс
})
```

## Цикл рендеринга в 4 шага.

Каждый раз когда стейт изменился и пришло время обновить DOM, WEX запускает функцию `render`. 
Внутри неё происходят четыре фазы строго по порядку: `prepare` → `compile` → `diffAndPatch` → `affect`

### 1. prepare — сброс эффектов

Перед новым рендером WEX обходит все ранее зарегистрированные записи скомпилированных узлов 
и вызывает у каждого функцию `revoke` — если она есть. Это чистка побочных эффектов прошлого 
рендера: снятие обработчиков событий, отписки от наблюдателей.

Именно поэтому `w-bind` не накапливает бесконечные `input`-листенеры при каждом ре-рендере 
— каждый прошлый листенер аккуратно снимается перед новым рендером.

### 2. compile — виртуальное дерево

WEX берёт HTML-строку из вашего `<template>` и строит из неё новое дерево узлов — 
но не в реальный DOM, а в отдельный `<div>` в памяти. На этом этапе:
- обрабатываются все директивы (`w-for`, `w-if`, `w-class` и остальные)
- интерполируются все `{{ выражения }}`
- создаются или переиспользуются экземпляры дочерних компонентов

Результат — массив готовых DOM-узлов, которые пока ни к чему не подключены.

### 3. diffAndPatch — умное обновление

Вот здесь и живёт главная оптимизация. WEX не заменяет весь DOM — 
он сравнивает только что скомпилированное дерево с тем что уже стоит 
на странице, и точечно обновляет только то что изменилось.

Было в DOM:       Пришло новое:    Итог:
<li>Хлеб</li>     <li>Хлеб</li>    → не тронуто
<li>Молоко</li>   <li>Кефир</li>   → textContent обновлён
<li>Сыр</li>      (нет)            → удалён

При сравнении узлов WEX смотрит на `id`, `data-id` и `w-id` — именно поэтому 
`traceby` в `w-for` так важен. Без него фреймворк ориентируется только 
по позиции и типу тега, что менее точно.

### 4. affect — живые эффекты
После того как DOM обновлён, WEX проходит по всем скомпилированным 
записям ещё раз и запускает функции `affect` — это финальная фаза 
где директивы получают доступ к реальным DOM-элементам. 
Именно здесь `w-bind` вешает input-листенер, `w-src` ставит настоящий 
`src` на картинку, `w-on` регистрирует обработчик событий через `view.on`.

Разделение `compile` и `affect` сделано намеренно: на этапе компиляции 
элементы ещё не в DOM, события на них вешать бессмысленно.

## Как w-static выключается из этого цикла

Теперь понятно почему w-static такой эффективный. Заглянув в исходник 
можно увидеть что это вовсе не специальная директива — это компонент, 
который подписывается на внутреннее событие $update и немедленно вызывает prevent():
```js 
component(
  'w-static',
  () => $('<template><slot></slot></template>')
    .vm()
    .on('$update', () => (e, state, prevent) => {
      prevent()  // ← просто говорит "не надо меня перерисовывать"
    })
)
```

Первый рендер проходит нормально. При каждом последующем вызове `render` 
— компонент блокирует фазу `compile` для своего поддерева. 
До `diffAndPatch` дело просто не доходит.

## Вся картина целиком
```
   Изменился стейт
      ↓
   Proxy перехватил
      ↓
   nextTick (ждём 16мс, собираем все изменения)
      ↓
   render()
      ↓
   prepare()        — снимаем старые эффекты
      ↓
   compile()        — строим новое дерево в памяти
      ↓             ↑
      |             w-static → prevent() → стоп, этот узел пропускаем
      ↓
   diffAndPatch()   — сравниваем с реальным DOM, патчим точечно
      ↓
   affect()         — вешаем живые эффекты на реальные элементы
      ↓
   DOM обновлён.
```

Именно эта архитектура делает WEX предсказуемым: стейт — 
единственный источник правды, DOM — лишь его отражение. 
Вы никогда не трогаете DOM напрямую, а фреймворк сам разбирается 
что изменить, что оставить и что пропустить совсем.

# Хранилище (Store)

Представьте что пользователь набрал очки в игре, заполнил форму 
или выбрал тему оформления — и вдруг обновил страницу. 
Всё сбросилось. Стейт WEX живёт только в памяти браузера, 
и при перезагрузке возвращается к начальным значениям.
Чтобы этого не происходило, в WEX есть встроенный механизм сохранения — Store. 

Достаточно положить нужные данные в специальный ключ стейта с именем storage, 
и фреймворк автоматически будет синхронизировать их с localStorage браузера. 
Данные переживут перезагрузку, закрытие вкладки и возврат на страницу.

```html 
<template id="score">
    <p>Score: {{ storage.score }}</p>
    <button class="increase-btn">Increase</button>
</template>

<script>
    $('#score')
        .state({
            storage: {
                score: 0,
                test: 1,
            }
        })
        .on('click', '.increase-btn', state => {
            state.storage.score = ++state.storage.score;
        })
        .mount()
</script>
```

Всё что находится внутри `storage` — сохраняется. Всё что снаружи — 
живёт только до перезагрузки. Это намеренное разделение: 
вы сами решаете что важно сохранить, а что нет.

## Что происходит под капотом

WEX следит за `storage` в двух точках жизненного цикла:

При монтировании (`$mount`) — фреймворк смотрит есть ли в `localStorage` 
сохранённые значения для каждого ключа из `storage`. Если есть — загружает 
их в стейт, и пользователь видит свои прошлые данные. Если нет — записывает 
текущие начальные значения как точку отсчёта.

При каждом изменении стейта (`$change`) — если данные в `storage` изменились, 
они немедленно записываются в `localStorage`. Синхронизация происходит автоматически, 
вам не нужно ничего вызывать вручную.

```
Первый визит:          Повторный визит:
-------------------------------------------------
storage.score = 0      localStorage → score = "7"
```

## Что хранить в storage
Store хорошо подходит для данных которые должны пережить перезагрузку:
- счётчики и прогресс
- выбранный язык или тема оформления
- содержимое корзины
- состояние формы которую пользователь не дозаполнил
- любые пользовательские настройки

```js 
$('#app')
    .state({
        theme: 'light',       // ← не сохранится
        username: '',         // ← не сохранится
        storage: {
            lang: 'ru',       // ← сохранится
            fontSize: 16,     // ← сохранится
            darkMode: false,  // ← сохранится
        }
    })
    .mount()
```

## Важно знать!
⚠ localStorage хранит только строки. WEX автоматически сериализует 
значения через JSON.stringify при записи и JSON.parse при чтении. 
Это означает что числа, булевы значения и вложенные объекты работают 
корректно — но при чтении из пустого хранилища всегда проверяйте 
что значение не null.

⚠ localStorage ограничен объёмом около 5 МБ на домен. 
Для хранения больших массивов данных или файлов он 
не подходит — держите в storage только лёгкие настройки и счётчики.

⚠ Данные в localStorage привязаны к домену и браузеру. 
Если пользователь откроет сайт в другом браузере или 
режиме инкогнито — история не перенесётся.

# Хуки жизненного цикла
Любой компонент в WEX проходит через определённые этапы — появляется на странице, 
обновляется когда меняются данные, и в какой-то момент исчезает. 

Хуки — это способ встроиться в эти этапы и выполнить свой код в нужный момент.

Технически это обычный `.on()`, но вместо DOM-событий вроде `click` или 
`input` — специальные внутренние события, которые начинаются с `$`. 
WEX сам вызывает их в нужное время, вам остаётся только подписаться.

## $mount — компонент появился на странице

Срабатывает один раз, сразу после того как вью вставлена в DOM. 
Идеальное место для загрузки начальных данных, запросов к API или любой инициализации:

```html 
<template id="app">
    <div w-if="!!loading">Загрузка...</div>
    <div w-if="!loading">
        <p>Привет, {{ username }}!</p>
    </div>
</template>

<script>
    $('#app')
      .state({ username: '', loading: true })
      .on('$mount', state => {
          setTimeout(() => {
              state.username = 'Алиса';
              state.loading = false;
          }, 1500)
      })
      .mount()
</script>
```

Пользователь видит «Загрузка...» пока данные не пришли — затем 
WEX автоматически перерисовывает шаблон.

## $unmount — компонент убран со страницы

Срабатывает когда вы вызываете `view.unmount()`. Место для чистки — остановить таймеры, 
отписаться от внешних событий, сбросить что-то в исходное состояние:
```html 
<template id="timer">
    <p>Прошло секунд: {{ seconds }}</p>
    <button class="stop-btn">Остановить</button>
</template>

<script>
    let interval = null;

    const view = $('#timer')
      .state({ seconds: 0 })
      .on('$mount', state => {
          interval = setInterval(() => {
              state.seconds++;
          }, 1000);
      })
      .on('$unmount', state => {
          clearInterval(interval);
      })
      .on('click', '.stop-btn', state => {
          view.unmount();
      })
      .mount()
</script>
```
Без `$unmount` таймер продолжал бы тикать в фоне даже после исчезновения компонента.

## $change — стейт изменился

Срабатывает каждый раз когда любое значение в стейте меняется. 
Удобно для слежения за данными, логирования или синхронизации с внешними системами:
```html 
<template id="form">
    <input w-bind="query" placeholder="Введите запрос">
    <p>Символов: {{ length }}</p>
</template>

<script>
    $('#form')
      .state({ query: '', length: 0 })
      .on('$change', state => {
          state.length = state.query.length;
      })
      .mount()
</script>
```

⚠ Будьте осторожны — если внутри `$change` снова менять стейт, это вызовет ещё один `$change`. 
Следите чтобы не получилась бесконечная цепочка.

## $render — шаблон перерисован

Срабатывает после каждой перерисовки DOM. Нужен когда важно работать с реальными 
элементами уже после того как они появились или обновились — например 
инициализировать стороннюю библиотеку:

```html 
<template id="chart">
    <canvas class="my-canvas"></canvas>
</template>

<script>
    $('#chart')
      .state({ data: [10, 20, 30] })
      .on('$render', state => {
          // canvas уже в DOM, можно рисовать
          const canvas = document.querySelector('.my-canvas');
          // ... инициализация графика
      })
      .mount()
</script>
```

## $destroy — компонент уничтожен

Срабатывает при вызове view.destroy() — это жёстче чем unmount. 
Компонент не просто скрывается, а полностью удаляется вместе 
со всеми подписками. Используется для финальной очистки:

```js 
const view = $('#app')
  .state({ ... })
  .on('$destroy', state => {
      console.log('Компонент уничтожен, прощай')
      // финальная очистка, освобождение ресурсов
  })
  .mount()

// Где-то позже:
view.destroy()
```

## Вся цепочка жизни компонента
```
   .mount() вызван
      ↓
   $mount — компонент в DOM, можно инициализировать
      ↓
   стейт изменился
      ↓
   $change — данные обновились
      ↓
   $render — DOM перерисован
      ↓
   .unmount() вызван
      ↓
   $unmount — компонент ушёл, чистим за собой
      ↓
   .destroy() вызван
      ↓
   $destroy — всё, компонент больше не существует
```

## Сравнение хуков

    Хук    |      Когда срабатывает        |    Типичное применение
-----------+-------------------------------+-----------------------------------
`$mount`   | Один раз, при появлении в DOM | Загрузка данных, запросы
`$change`  | При каждом изменении стейта   | Слежение, синхронизация
`$render`  | После каждой перерисовки      | Работа со сторонними библиотеками
`$unmount` | При скрытии компонента        | Очистка таймеров, отписки
`$destroy` | При полном уничтожении        | Финальная очистка ресурсов
`$route`   | 
`$wiring`  |

# Синхронизация компонентов между собой общим стейтом

Когда компонентов на странице становится больше одного, возникает естественный 
вопрос: а что если им нужно работать с одними и теми же данными?

Представьте корзину на сайте. Счётчик товаров в шапке, список товаров в боковой 
панели и итоговая сумма в футере — три разных компонента, но все они должны 
знать об одном и том же: что сейчас лежит в корзине. Если каждый хранит свою 
копию стейта — они начнут расходиться и показывать разное.

Store — это единый стейт который несколько компонентов разделяют между собой. 
Меняется значение в одном месте — все компоненты которые его используют 
обновляются одновременно автоматически.

## Как это работает

```js
// Создаём общий стейт — один на всех
const store = shareState({ count: 10 })

// Оба компонента получают один и тот же store вместо своего стейта
const componentA = $('<span>Значение: {{count}}</span>')
  .state(store)

const componentB = $('<div>count: {{count}}</div>')
  .state(store)
```

```html 
<template id="app">
    <comp-a></comp-a>
    <comp-b></comp-b>
</template>
```

```js 
$('#app').state({})
  .component('comp-a', componentA)
  .component('comp-b', componentB)
  .mount()
```

Оба компонента видят одно и то же count. Если count изменится — оба перерисуются.

## Реальный пример — счётчик корзины

Сделаем кнопку добавления товара и счётчик в шапке — два независимых 
компонента которые работают с одними данными:

```js
// Единый источник правды для всей страницы
const cartStore = shareState({
    itemCount: 0,
    total: 0,
})

// Шапка — только показывает
const cartBadge = $(`
    <template>
        <div class="cart-badge">
            🛒 <span>{{ itemCount }}</span>
        </div>
    </template>
`)
  .state(cartStore)

// Кнопка — только добавляет
const addToCart = $(`
    <template>
        <button class="add-btn">Добавить в корзину ({{ itemCount }})</button>
    </template>
`)
  .state(cartStore)
  .on('click', '.add-btn', state => {
      state.itemCount++
  })
```

```html 
<template id="app">
    <cart-badge></cart-badge>

    <main>
        <h2>Товар: Хлеб — 45 ₽</h2>
        <add-to-cart></add-to-cart>
    </main>
</template>

<script>
    $('#app').state({})
      .component('cart-badge', cartBadge)
      .component('add-to-cart', addToCart)
      .mount()
</script>
```

Нажали кнопку — itemCount вырос на единицу в cartStore — оба компонента мгновенно 
перерисовались с новым значением. Никакой передачи данных через пропсы, никаких 
событий наверх — просто общий стейт.

## Store + localStorage

Store прекрасно сочетается с механизмом storage который мы разбирали раньше. 
Достаточно добавить ключ storage в createStore — и общий стейт автоматически 
переживёт перезагрузку страницы:

```js 
const cartStore = shareState({
    storage: {
        itemCount: 0,
        total: 0,
    }
})
```

Теперь пользователь добавил товары, закрыл вкладку, вернулся — корзина на месте. 
И по-прежнему все компоненты синхронизированы между собой.

## Когда использовать Store, а когда пропсы

Не каждый стейт нужно выносить в Store. Хорошее правило:

Пропсы — когда данные принадлежат родителю и он осознанно передаёт их вниз. 
Например, родитель знает имя пользователя и передаёт его в дочерний компонент-приветствие.

Store — когда данные нужны нескольким компонентам которые не знают друг о друге и не имеют 
общего родителя. Корзина, авторизация, выбранная тема — всё что является глобальным 
состоянием приложения.

```
Локальный стейт    →  данные нужны только этому компоненту
Пропсы             →  родитель осознанно делится данными с ребёнком
Store              →  данные нужны нескольким несвязанным компонентам
```

``` 
Store это не серебряная пуля — не стоит тащить туда всё подряд. 
Если данные нужны только одному компоненту, пусть живут в его локальном стейте. 

Store появляется тогда, когда без него начинается неудобная передача данных 
через длинные цепочки пропсов или костыльные глобальные переменные.
```

# Асинхронные компоненты

Когда приложение растёт, на одной странице может собраться десяток компонентов. 
Если грузить их все сразу — пользователь ждёт пока загрузится всё, даже то что ему 
сейчас не нужно. Модальное окно которое откроется только если нажать кнопку, редактор 
который появится только в режиме редактирования — зачем тащить их при первой загрузке?

Асинхронный компонент — это компонент который загружается только тогда когда действительно 
понадобился. Страница открывается быстро с минимумом кода, а тяжёлые части подгружаются 
по требованию в фоне.

## Простейший случай — ленивая загрузка модуля

Компонент живёт в отдельном JS-файле и загружается только когда страница его запрашивает:
```js 
// components/user-card.js — отдельный файл
export default $(`
    <template>
        <div class="user-card">
            <h3>{{ name }}</h3>
            <p>{{ email }}</p>
        </div>
    </template>
`)
  .state(() => ({ name: '', email: '' }))
```
```js 
// main.js — основной файл
const { createAsyncComponent } = window.jqvm

$('#app')
  .state({ user: { name: 'Алиса', email: 'alice@astre.ws' } })
  .component(
      'user-card',
      createAsyncComponent(() => import('./components/user-card.js'))
  )
  .mount()
```
```html 
<template id="app">
    <user-card :name="user.name" :email="user.email"></user-card>
</template>
```
Браузер загрузит `user-card.js` отдельным запросом — и только тогда когда шаблон 
встретит тег `<user-card>`. До этого момента файл не скачивается вовсе.

## Загрузка с индикатором — реальный сценарий

Асинхронная загрузка занимает время, и пользователь должен понимать что что-то происходит. 
Для этого у `createAsyncComponent` есть второй аргумент — `callback` который вызывается когда 
компонент загрузился:
```html 
<template id="app">
    <div w-if="!!loading" class="spinner">
        Загружаем редактор...
    </div>
    <rich-editor w-if="!loading"></rich-editor>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({ loading: true })
        .component(
            'rich-editor',
            createAsyncComponent(
                // loader — как загрузить компонент
                () => import('./components/rich-editor.js'),

                // callback — что сделать когда загрузился
                function() {
                    this.update({ loading: false })
                }
            )
        )
        .mount()
</script>
```
Пользователь видит спиннер пока компонент грузится. Как только загрузка завершилась 
— loading становится false, спиннер исчезает, редактор появляется.

## Загрузка HTML с сервера

Компонент не обязательно должен быть JS-модулем. Можно загрузить HTML прямо с сервера 
через Ajax — удобно когда шаблоны живут на бэкенде:

```js 
$('#app')
  .state({ loading: true })
  .component(
      'product-table',
      createAsyncComponent(
          // загружаем HTML через jQuery Ajax
          () => $.get('/components/product-table.html')
            .then((html) => {
                return $(html).vm(() => ({
                    products: [],
                    sortBy: 'name',
                }))
            }),

          function() {
              this.update({ loading: false })
          }
      )
  )
  .mount()
```

Сервер отдаёт кусок HTML, WEX оборачивает его в вью с нужным стейтом — и компонент готов. 
Это особенно хорошо сочетается с PHP и Blade: шаблоны хранятся на сервере, 
подгружаются по необходимости, данные приходят реактивно.

## Реальный кейс — тяжёлый редактор по клику

Самый частый сценарий применения — откладывать загрузку тяжёлых компонентов до момента 
когда пользователь явно их запросил:
```html 
<template id="app">
    <div w-if="!editorOpen">
        <p>{{ previewText }}</p>
        <button class="edit-btn">Редактировать</button>
    </div>

    <div w-if="!!editorOpen">
        <div w-if="!!editorLoading">Загружаем редактор...</div>
        <obsidian-editor w-if="!editorLoading"></obsidian-editor>
        <button class="cancel-btn">Отмена</button>
    </div>
</template>

<script>
    const { createAsyncComponent } = window.jqvm

    $('#app')
        .state({
            previewText: 'Нажмите редактировать чтобы изменить текст.',
            editorOpen: false,
            editorLoading: false,
        })
        .component(
            'obsidian-editor',
            createAsyncComponent(
                () => import('./components/obsidian-editor.js'),
                function() {
                    this.update({ editorLoading: false })
                }
            )
        )
        .on('click', '.edit-btn', state => {
            state.editorOpen   = true
            state.editorLoading = true
        })
        .on('click', '.cancel-btn', state => {
            state.editorOpen   = false
            state.editorLoading = false
        })
        .mount()
</script>
```

Пользователь открывает страницу — редактор даже не начинает загружаться. 
Нажал «Редактировать» — только тогда браузер идёт за файлом. 
Тяжёлые библиотеки не тормозят первую загрузку страницы.

## Когда использовать асинхронные компоненты

Не каждый компонент нужно делать асинхронным — это усложняет код и добавляет лишний 
сетевой запрос. Хорошие кандидаты:

Грузите асинхронно если компонент тяжёлый (редакторы, графики, карты), показывается 
не сразу (модалки, табы, аккордеоны) или нужен только части пользователей 
(формы редактирования, админские панели).

Грузите сразу если компонент маленький, нужен при первой загрузке или 
является частью основного интерфейса который пользователь видит всегда.

```
Маленькая кнопка, иконка           → обычный компонент
Шапка сайта, главное меню          → обычный компонент
Модальное окно                     → async
Текстовый редактор                 → async
Интерактивная карта                → async
Графики и дашборды                 → async
Форма которая открывается по клику → async
```

```
Асинхронные компоненты — это не оптимизация ради оптимизации. 
Это инструмент для конкретной задачи: сделать первую загрузку страницы быстрой, 
а тяжёлые части подтягивать только тогда когда они действительно нужны.
```

# Компоненты

Если вы пришли из мира jQuery, скорее всего ваш код выглядит примерно так: 
большой HTML-файл, много $('.что-то').on(...), и всё в одном месте. 
Это работает — но когда проект растёт, один и тот же кусок разметки 
начинает копироваться по странице, а правка в одном месте требует правки 
во всех остальных.

Компонент — это переиспользуемый кусок шаблона со своим стейтом. 
Один раз описали карточку товара, кнопку или иконку — и вставляете их в 
любое место как обычный HTML-тег. WEX сам разберётся как это отрисовать.

## Первый компонент — иконка

Представьте что по всему сайту используются иконки, и каждый раз писать 
`<i class="icon icon-search"></i>` надоело. Вынесем это в компонент:

```js 
const { component } = window.jqvm

const icon = $(`<i class="icon icon-{{type}}"></i>`)
  .state(() => ({ type: 'eye' })) // начальное значение по умолчанию

component('icon', icon)
```

Теперь в любом шаблоне можно писать просто:
```html 
<template id="app">
    <icon type="search"></icon>
    <icon type="heart"></icon>
    <icon type="user"></icon>
</template>
```

WEX подставит нужный тип и каждый раз отрисует правильную иконку. 
Захотели изменить структуру иконки — меняете в одном месте, обновится везде.

```
Заметьте: в .state() передаётся функция, которая возвращает объект — 
а не сам объект напрямую. Это важно: каждый экземпляр компонента 
получает свою независимую копию стейта. Если передать объект напрямую — 
все иконки на странице будут делить один стейт и менять друг друга.
```

## Пропсы — передача данных внутрь

Пропсы это то что вы передаёте компоненту снаружи — как атрибуты HTML-тега. 
Есть три способа:

Обычная строка — просто пишете значение:
```html 
<icon type="search"></icon>
```
Выражение из стейта — ставите : перед именем, 
и WEX вычислит значение из текущего стейта родителя:
```html 
<icon :type="currentIcon"></icon>
<!-- currentIcon берётся из state родительского шаблона -->
```
Функция-обработчик — ставите @, чтобы компонент мог сообщить родителю о событии:
```html 
<my-button @click="handleClick"></my-button>
```

Важное ограничение: работают только те пропсы, которые объявлены в стейте компонента. 
Если в стейте компонента нет ключа color — передать color="red" снаружи не получится, 
атрибут просто проигнорируется.

```html 
// стейт компонента
.state(() => ({ type: 'eye', size: 'md' }))

// ✓ сработает — оба ключа есть в стейте
<icon type="search" size="lg"></icon>

// ✗ не сработает — color нет в стейте компонента
<icon type="search" color="red"></icon>
```

## Компонент карточки — реальный пример

Сделаем компонент карточки товара, который можно переиспользовать в каталоге:
```js 
const productCard = $(`
    <template>
        <div class="card">
            <img w-src="image" alt="Фото">
            <h3>{{ name }}</h3>
            <p>{{ price }} ₽</p>
            <button class="buy-btn">Купить</button>
        </div>
    </template>
`)
  .state(() => ({
      name: '',
      price: 0,
      image: '',
  }))
  .fn('buy', state => function(e) {
      alert(`Добавлено в корзину: ${state.name}`)
  })
  .on('click', '.buy-btn', function(state) {
      this.fn('buy')(state)
  })

component('product-card', productCard)
```

Используем в шаблоне через w-for:
```html 
<template id="catalog">
    <div class="catalog">
        <product-card
            w-for="item in products traceby item.id"
            :name="item.name"
            :price="item.price"
            :image="item.image">
        </product-card>
    </div>
</template>

<script>
    $('#catalog')
      .state({
          products: [
              { id: 1, name: 'Хлеб',   price: 45,  image: '/img/bread.jpg'  },
              { id: 2, name: 'Молоко', price: 89,  image: '/img/milk.jpg'   },
              { id: 3, name: 'Сыр',    price: 320, image: '/img/cheese.jpg' },
          ]
      })
      .mount()
</script>
```
Три карточки — три независимых компонента, каждый со своим стейтом.

## Эмиттер — компонент говорит с родителем

Пока что данные шли только в одну сторону: родитель передаёт пропсы — компонент 
их отображает. Но что если компонент хочет сообщить родителю что что-то произошло? 
Для этого есть `emit`.

Представьте компонент-счётчик, который должен уведомлять родителя об изменении значения:
```js 
const counter = $(`
    <template>
        <button class="minus-btn">−</button>
        <span>{{ count }}</span>
        <button class="plus-btn">+</button>
    </template>
`)
  .state(() => ({ count: 0 }))
  .on('click', '.plus-btn', state => function() {
      state.count++
      this.emit('change', state.count) // ← сообщаем родителю
  })
  .on('click', '.minus-btn', state => function() {
      state.count--
      this.emit('change', state.count) // ← сообщаем родителю
  })

component('counter', counter)
```
Родитель подписывается через `@change` и регистрирует обработчик через `.fn()`:
```html 
<template id="app">
    <counter @change="onCountChange"></counter>
    <p>Родитель знает: {{ total }}</p>
</template>

<script>
    $('#app')
      .state({ total: 0 })
      .fn('onCountChange', state => function(newCount) {
          state.total = newCount
      })
      .mount()
</script>
```
Компонент живёт своей жизнью внутри, но в нужный момент «кричит наружу» 
через `emit` — родитель слышит и реагирует.

## Локальный компонент vs глобальный

Если компонент нужен только в одном конкретном шаблоне — регистрируйте его 
локально через `.component()` прямо на вью. Если нужен по всему приложению — 
регистрируйте глобально через `component()` из импорта:

```js 
// Глобально — доступен везде
const { component } = window.jqvm
component('my-icon', icon)

// Локально — только для этого шаблона
$('#app')
  .state({ ... })
  .component('my-icon', icon) // ← метод самого вью
  .mount()
```

## Вся идея в одной строке

Компоненты в WEX — это те же самые вью, просто вложенные друг в друга. 
Всё что умеет обычный шаблон: стейт, директивы, хуки, `w-for`, `w-if` — 
всё это работает и внутри компонента. Никакого нового синтаксиса учить не нужно.

# Серверные компоненты и современные парадигмы рендеринга

Прежде чем разбирать архитектуру — нужно понять картину целиком. 
Откуда вообще берётся HTML который видит пользователь, и почему это важно.

## Откуда приходит HTML

Существует три принципиально разных ответа на этот вопрос.

### CSR — Client Side Rendering. 
Сервер отдаёт почти пустую страницу и большой JavaScript-файл. 
Браузер скачивает JS, выполняет его, и только тогда на экране появляется контент. 
Именно так работают React, Vue и Angular по умолчанию. 
Пользователь первые секунды смотрит на белый экран или спиннер. 
Поисковый робот видит то же самое — пустоту — и с трудом индексирует контент.

### SSR — Server Side Rendering. 
Сервер каждый раз при запросе генерирует готовый HTML 
и отдаёт его браузеру. Пользователь видит контент мгновенно. Поисковик получает 
полноценную страницу. PHP с Blade, Ruby on Rails, Django — классические примеры SSR. 
Это не новомодная идея, а то как веб работал изначально.

### SSG — Static Site Generation. 
HTML генерируется один раз заранее — при сборке проекта 
— и раздаётся всем пользователям как статический файл. Максимально быстро, 
но не подходит для динамических данных. Например, кэширование Blade в Laravel.

```
CSR:  Запрос → пустой HTML + JS → браузер рисует → контент
SSR:  Запрос → сервер думает → готовый HTML → контент
SSG:  Сборка → готовый HTML → Запрос → контент (мгновенно)
```

## В чём проблема чистого CSR

Next.js, Nuxt, SvelteKit — все эти фреймворки появились именно потому что 
CSR оказался неудобен для реального бизнеса. Пришлось изобретать 
«серверные компоненты» поверх изначально клиентских фреймворков. 

Получилось сложно: в Next.js нужно явно писать 'use client' чтобы объяснить 
фреймворку что этот компонент интерактивный, а тот — нет. Два режима, 
два способа мышления, много нюансов.

PHP-first подход переворачивает это с головы на ноги. 
По умолчанию всё серверное — SEO из коробки, быстрая загрузка, никакого белого экрана. 
А туда где нужна интерактивность — аккуратно добавляется WEX.

## Серверный компонент vs клиентский компонент

Серверный компонент — это Blade-шаблон, Twig, Jinja или любой другой шаблонизатор. 
Он живёт на сервере, видит базу данных, знает кто авторизован, имеет доступ 
к переменным окружения. Его результат — готовый HTML, который летит в браузер.

Клиентский компонент — это WEX-вью. Он живёт в браузере, реагирует на действия 
пользователя, обновляет интерфейс без перезагрузки страницы.

          Описание            |   Серверный (Blade)  | Клиентский (WEX)
------------------------------+---------------------+-------------------------
Где выполняется               | PHP-сервер           | Браузер пользователя
Видит БД                      | ✓ напрямую           | ✗ только через API
Виден поисковикам             | ✓ сразу              | зависит от данных
Реагирует на клики            | ✗                    | ✓
Обновляется без перезагрузки  | ✗                    | ✓
Хранит стейт                  | ✗                    | ✓

Они не конкуренты — они партнёры. Каждый делает то, что умеет лучше.

## Базовая архитектура — просто

В простейшем случае всё выглядит так: Blade рисует страницу, 
WEX добавляет жизнь туда где она нужна.

```bladehtml
{{-- resources/views/products/index.blade.php --}}

<h1>Каталог товаров</h1>

{{-- Это серверный HTML — поисковик его прочитает --}}
@foreach($products as $product)
    <div class="product-card">
        <h2>{{ $product->name }}</h2>
        <p>{{ $product->price }} ₽</p>
    </div>
@endforeach

{{-- А это уже WEX — только для интерактивного фильтра --}}
<template id="filter">
    <input w-bind="query" placeholder="Поиск по каталогу">
    <div w-if="query.length > 0">
        Ищем: {{ query }}
    </div>
</template>

<script>
    $('#filter').state({ query: '' }).mount()
</script>
```

Товары отрендерил PHP — их увидит Google. Поиск с живой фильтрацией 
добавил WEX — пользователь получил интерактивность.

## Масштабная архитектура

Когда WEX-компонент становится сложным — он начинает обрастать кодом. 
Всё в одном `<script>` становится нечитаемо. Именно здесь Blade раскрывается 
как инструмент организации JavaScript-кода.

Посмотрите на пример следующей структуры моего компонента Obsidian:
```
obsidian/
├── bootstrap.blade.php     ← создаёт глобальный объект window.Obsidian
├── state.blade.php         ← описывает начальный стейт
├── factory.blade.php       ← фабрика: собирает вью из частей
├── hooks/
│   ├── mount.blade.php     ← логика при монтировании
│   └── update.blade.php    ← логика при обновлении
└── actions/
    └── fullscreen.blade.php ← конкретные действия
```
Каждый файл — один маленький <script> с одной ответственностью. 
Blade просто склеивает их в нужном порядке через @include. 
Никакого webpack, никакого npm — только PHP и браузер.

### Фабрика собирает готовый компонент из кусков:

```js 
// factory.blade.php
window.Obsidian.init = function(selector, overrides) {
    return $(selector)
        .state(Obsidian.State(overrides))     // ← из state.blade.php
        .on('$mount',  Obsidian.Hooks.mount)  // ← из hooks/mount.blade.php
        .on('$update', Obsidian.Hooks.update) // ← из hooks/update.blade.php
        .on('click', '.toggle-fullscreen-btn', Obsidian.Hooks.toggleFullscreen)
        .mount();
};
```

А использовать его на любой странице теперь одной строкой:
```bladehtml
{{-- любая страница где нужен редактор --}}
<template id="editor-1"></template>

<script>
    Obsidian.init('#editor-1')
</script>
```

Хотите второй редактор с другим начальным контентом — просто передаёте overrides:
```bladehtml
Obsidian.init('#editor-2', {
    storage: { content: 'Начальный текст...' }
})
```

## Когда совмещать, а когда нет

Хорошее правило: если данные нужны поисковику или должны появиться 
мгновенно — это работа сервера. Если данные появляются в ответ 
на действие пользователя — это работа WEX.

Отдавайте серверу:
- каталоги, статьи, карточки товаров — всё что индексируется
- данные из базы которые не меняются без действия пользователя
- авторизацию и права доступа
- начальное состояние страницы

Отдавайте WEX:
- формы и их валидацию
- фильтры, сортировки, поиск
- модальные окна, табы, аккордеоны
- всё что меняется без перезагрузки страницы
- счётчики, корзины, лайки

## Реальные кейсы:
Интернет-магазин — каталог рендерит PHP (SEO), но фильтр по цене и 
добавление в корзину делает WEX (интерактивность).

Блог — статьи отдаёт сервер (поисковик читает полный текст), но форма 
комментариев с live-preview работает через WEX.

Админ-панель — здесь SEO не нужен вовсе, зато нужна богатая интерактивность. 
Blade даёт структуру и авторизацию, WEX берёт на себя весь UI.

## Главная идея

В мире React и Next.js SSR — это дополнение которое нужно специально 
подключать и настраивать. В мире PHP — SSR это просто то как всё 
работает по умолчанию, и WEX добавляется точечно туда где нужна интерактивность.

Это не компромисс и не костыль — это честное разделение труда. 
Сервер делает то в чём он силён, браузер делает то в чём силён он. 
Пользователь получает быструю страницу, поисковик — полноценный контент, 
разработчик — простую и понятную архитектуру без магии.

```
Пример с Obsidian показывает что даже сложный интерактивный компонент 
— редактор с fullscreen-режимом, подсчётом слов и сохранением в localStorage 
— можно построить на этой связке аккуратно и читаемо. Blade организует файлы, 
WEX управляет стейтом, каждый занимается своим делом.
```

# Фильтры

Представьте что в стейте лежит число `1990.5`.
Вывести его напрямую через `{{ price }}` — получите `1990.5`. Но пользователю хочется 
показать `1 990,50 $`. Можно написать функцию форматирования и вызывать 
её везде вручную — но это быстро превращается в повторяющийся код раскиданный 
по всему шаблону.

Фильтр — это функция-форматировщик которая применяется прямо 
в шаблоне через символ `|`. Один раз описали правило преобразования — 
используете везде одной строкой.

```html 
<div>{{ price | number:2 }}</div>
```

```js 
view.filter('number', function(value, fixed) {
    return value.toFixed(fixed)
})
```

Читается как «возьми price и прогони через фильтр number с аргументом 2».

## Реальные кейсы

### Форматирование цены. 

Самый частый случай — привести число к красивому денежному виду:
```html 
<template id="app">
    <p>Цена: {{ price | currency }}</p>
    <p>Скидка: {{ oldPrice | currency }}</p>
</template>

<script>
    $('#app')
            .state({ price: 1990.5, oldPrice: 2500 })
            .filter('currency', function(value) {
                return value.toLocaleString('ru-RU', {
                    style: 'currency',
                    currency: 'RUB'
                })
            })
            .mount()

    // Выведет: 1 990,50 ₽ и 2 500,00 ₽
</script>
```

### Дата в человекочитаемом виде. 

Из базы данных обычно приходит строка вроде `2024-03-15T10:30:00` — 
пользователю это показывать не стоит:
```html 
<template id="app">
    <div w-for="post in posts traceby post.id">
        <h3>{{ post.title }}</h3>
        <span>{{ post.createdAt | date }}</span>
    </div>
</template>

<script>
    $('#app')
        .state({
            posts: [
                { id: 1, title: 'Первая статья', createdAt: '2024-03-15T10:30:00' },
                { id: 2, title: 'Вторая статья', createdAt: '2024-01-22T08:00:00' },
            ]
        })
        .filter('date', function(value) {
            return new Date(value).toLocaleDateString('ru-RU', {
                day: 'numeric',
                month: 'long',
                year: 'numeric'
            })
        })
        .mount()

    // Выведет: 15 марта 2024 г. и 22 января 2024 г.
</script>
```

### Обрезка длинного текста. 
Для карточек и превью часто нужно ограничить количество символов:
```html 
<template id="app">
    <div w-for="article in articles traceby article.id">
        <h3>{{ article.title }}</h3>
        <p>{{ article.body | truncate:120 }}</p>
    </div>
</template>

<script>
    $('#app')
        .state({ articles: [...] })
        .filter('truncate', function(value, limit) {
            if (value.length <= limit) return value
            return value.slice(0, limit).trimEnd() + '...'
        })
        .mount()
</script>
```

### Множественное число. 
Классическая задача — «1 товар», «2 товара», «5 товаров»:
```html 
<template id="app">
    <p>{{ count }} {{ count | plural:'товар,товара,товаров' }}</p>
</template>

<script>
    $('#app')
        .state({ count: 0 })
        .filter('plural', function(value, words) {
            const [one, few, many] = words.split(',')
            const mod10 = value % 10
            const mod100 = value % 100

            if (mod100 >= 11 && mod100 <= 19) return many
            if (mod10 === 1) return one
            if (mod10 >= 2 && mod10 <= 4) return few
            return many
        })
        .mount()

    // 1 товар, 3 товара, 11 товаров, 21 товар
</script>
```

## Цепочка фильтров

Фильтры можно применять последовательно — результат одного передаётся в следующий:
```html 
<template id="app">
    <p>{{ comment | truncate:80 | uppercase }}</p>
</template>

<script>
    $('#app')
        .state({ comment: 'очень длинный комментарий пользователя...' })
        .filter('truncate', function(value, limit) {
            return value.length > limit ? value.slice(0, limit) + '...' : value
        })
        .filter('uppercase', function(value) {
            return value.toUpperCase()
        })
        .mount()
</script>
```
Сначала обрежется до 80 символов, затем переведётся в верхний регистр.

## Глобальные фильтры

Если фильтр нужен по всему приложению — регистрируйте его глобально 
через импорт, чтобы не повторять в каждом шаблоне:

```js 
const { filter } = window.jqvm

filter('currency', function(value) {
    return value.toLocaleString('ru-RU', {
        style: 'currency',
        currency: 'RUB'
    })
})

filter('date', function(value) {
    return new Date(value).toLocaleDateString('ru-RU')
})

// Теперь {{ price | currency }} и {{ date | date }}
// работают в любом шаблоне на странице
```

## Когда фильтр, а когда вычисление в стейте

Фильтры — для отображения. Они не меняют исходные данные в стейте, 
только форматируют их на лету при выводе. Если вам нужно именно 
изменить данные и работать с ними дальше в логике — 
делайте это в стейте или в обработчике.

```js 
// ✓ Фильтр — только для показа, данные в стейте остаются числом
{{ price | currency }}   // в стейте: 1990.5, на экране: 1 990,50 ₽

// ✓ Вычисление в стейте — когда результат нужен в логике
state.total = state.items.reduce((sum, item) => sum + item.price, 0)
```

Хорошее правило: если задача «показать красиво» — фильтр. 
Если задача «посчитать и использовать» — стейт.

# Встроенный роутер

Прежде чем разбирать API — нужно понять саму идею. 

Когда пользователь переходит по ссылке на обычном сайте, браузер загружает новую 
страницу целиком. Роутер в WEX перехватывает эту навигацию и говорит браузеру: 
«не перезагружай страницу, я сам разберусь что показать». Адресная строка меняется, 
кнопка «назад» работает — но страница не перезагружается. Это и есть клиентский роутинг.

Под капотом роутер переписывает нативные `history.pushState` и `history.replaceState`, 
слушает `popstate` — и при любом изменении URL уведомляет вью чтобы та перерисовалась 
с учётом нового адреса.

## Подключение
Роутер подключается как плагин через `.plugin()`:
```js 
const { createRouter } = window.jqvm

const router = createRouter({ mode: 'hash' }) // или 'history'

$('#app')
  .state()
  .plugin(router)
  .mount()
```

## Два режима работы:
### hash-режим 
URL выглядит как site.ru/#/catalog. 
Работает везде без настройки сервера. 
Хэш-часть никогда не отправляется на сервер, роутер читает её сам.

### history-режим 
URL выглядит как site.ru/catalog. 
Красиво, но требует настройки сервера чтобы все пути возвращали 
один и тот же index.html. На Apache или Nginx это пара строк в конфиге.

## w-route — показать блок для конкретного маршрута
Это директива-аналог `w-if`, но условие — текущий URL а не стейт:

```html 
<template id="app">
    <nav>
        <a href="#/" w-navigate="push">Главная</a>
        <a href="#/catalog" w-navigate="push">Каталог</a>
        <a href="#/about" w-navigate="push">О нас</a>
    </nav>

    <div w-route="'/'">
        <h1>Добро пожаловать!</h1>
        <p>Это главная страница.</p>
    </div>

    <div w-route="'/catalog'">
        <h1>Каталог товаров</h1>
    </div>

    <div w-route="'/about'">
        <h1>О нас</h1>
    </div>
</template>

<script>
    $('#app').state().mount()
</script>
```

Заметьте: значение `w-route` — это выражение, поэтому строки пишутся 
в кавычках внутри кавычек: `w-route="'/catalog'"`.

## w-navigate — умные ссылки
Обычный `<a href>` вызовет полную перезагрузку страницы. `w-navigate` перехватывает клик 
и передаёт навигацию роутеру:

```html 
<!-- push — добавляет в историю (можно вернуться назад) -->
<a href="#/catalog" w-navigate="push">Каталог</a>

<!-- replace — заменяет текущую запись в истории -->
<a href="#/login" w-navigate="replace">Войти</a>

<!-- back / forward — как кнопки браузера -->
<button w-navigate="back">← Назад</button>
<button w-navigate="forward">Вперёд →</button>

<!-- open — новая вкладка -->
<a href="https://google.com" w-navigate="open">Открыть</a>
```

## Параметры в URL

Роутер умеет читать query-параметры из адресной строки — удобно для фильтров, 
страниц пагинации, ID записей:
```html 
<template id="app">
    <div w-route="'/catalog'">
        <p>Категория: {{ $route.params.category }}</p>
        <p>Страница: {{ $route.params.page }}</p>
        <button class="next-btn">Следующая страница</button>
    </div>
</template>

<script >
    const { createRouter } = window.jqvm
    const router = createRouter({ mode: 'hash' })

    $('#app')
        .state()
        .plugin(router)
        .fn('nextPage', function() {
            const { $router } = this
            return () => {
                const { params } = $router.getLocation()
                const current = parseInt(params.page) || 1
                $router.setParams({ page: current + 1 })
            }
        })
        .on('click', '.next-btn', function(state) {
            return this.fn('nextPage')(state)
        })
        .mount()
</script>
```

URL станет `#/catalog?category=shoes&page=2`. 
`$route.params` доступен прямо в шаблоне как часть стейта.

## Регулярные выражения в маршрутах

Для гибкого матчинга — например показать один блок для любой страницы 
товара — можно использовать регулярки:
```html 
<!-- Сработает для /product/1, /product/42, /product/anything -->
<div w-route="/^\/product\/.+/">
    <h1>Страница товара</h1>
</div>
```

## Реакция на смену маршрута

Хук `$route` срабатывает при каждом изменении URL — 
удобно для загрузки данных под новый маршрут:
```js 
$('#app')
  .vm({ products: [], loading: false })
  .plugin(router)
  .on('$route', (state, url) => {
      if (url === '/catalog') {
          state.loading = true
          $.get('/api/products').then(data => {
              state.products = data
              state.loading = false
          })
      }
  })
  .mount()
```

# Свои директивы.

Директивы — это пользовательские атрибуты которые WEX умеет обрабатывать 
при компиляции шаблона. Если встроенных директив не хватает — вы создаёте свои. 
Нужен атрибут `w-tooltip`, `w-animate`, `w-permission`? — директива именно для этого.

```js 
directive(name, compile, affect)
```

Два этапа обработки: `compile` — на стадии построения виртуального дерева, 
`affect` — когда элемент уже в реальном DOM.

## compile — изменить разметку до вставки в DOM

Вызывается когда WEX встречает ваш атрибут при компиляции шаблона. 
Элемент здесь виртуальный — его ещё нет на странице. Можно менять атрибуты, 
заменять содержимое, возвращать новый HTML.

```js 
const { directive } = window.jqvm

directive('w-link', function($el, attrs) {
    const link = attrs['w-link']
    $el.attr('href', link)
    // ничего не возвращаем — $el используется как есть
})
```
```html 
<template id="app">
    <a w-link="https://example.com">Ссылка</a>
</template>
```

Если вернуть строку — она заменит весь элемент:
```js 
directive('w-badge', function($el, attrs) {
    const count = attrs['w-badge']
    return `<span class="badge">${count}</span>`
    // оригинальный элемент заменён новым
})
```

⚠ `$el` в `compile` — это копия, не реальный DOM-элемент. 
Навешивать события здесь бессмысленно — они не сработают.

## affect — работать с реальным DOM

Вызывается после того как всё дерево скомпилировано и вставлено на страницу. 
Здесь `$el` — настоящий живой элемент. Можно вешать события, инициализировать плагины, читать размеры.
```js 
directive('w-src', null, function($el, attrs) {
    // this.scope.interpolate раскрывает {{ }} внутри значения
    const value = this.scope.interpolate(attrs['w-src'])
    $el.attr('src', value)
})
```
```html 
<img w-src="/images/{{user.avatar}}.jpg">
```
Это исходник встроенного `w-src` — именно так картинка не пытается загрузиться 
по буквальной строке `{{ user.avatar }}` во время компиляции.

## Очистка побочных эффектов

Если в `affect` вы вешаете обработчики или запускаете интервалы — верните функцию-очистку. 
WEX вызовет её перед каждым следующим рендером:

```js 
directive('w-click-outside', null, function($el, attrs) {
    const handler = (e) => {
        if (!$el[0].contains(e.target)) {
            $el.trigger('clickOutside')
        }
    }

    $(document).on('click', handler)

    return () => $(document).off('click', handler)
    // ↑ обязательно — иначе при каждом ре-рендере
    //   будет вешаться новый обработчик
})
```

Пример с инициализацией стороннего плагина:
```js 
directive('w-datepicker', null, function($el, attrs) {
    const picker = $el.datepicker({ format: attrs['w-datepicker'] || 'dd.mm.yyyy' })

    return () => picker.datepicker('destroy')
})
```
```html 
<input w-datepicker="yyyy-mm-dd">
```

## Локальная директива — только для одного шаблона

Глобальная директива через `window.state` работает во всех шаблонах страницы. 
Если директива нужна только в одном месте — регистрируйте её прямо на вью:
```js 
// глобально — доступна везде
const { directive } = window.jqvm
directive('w-highlight', ...)

// локально — только для этого шаблона
$('#app')
  .state({ ... })
  .directive('w-highlight', null, function($el, attrs) {
      $el.css('background', attrs['w-highlight'] || 'yellow')
  })
  .mount()
```

## Встроенные директивы

WEX поставляется с набором готовых директив. 
Все они работают по тем же правилам что описаны выше — просто уже написаны за вас.

- `w-if="!!exp"` — показать или скрыть элемент в зависимости от условия. Элемент физически отсутствует в DOM когда условие ложно.
- `w-for="value,index in data traceby value.id"` — перебор массива. `value,index` без пробела внутри, `,index` необязателен. traceby указывает уникальный ключ для точечного обновления DOM.
- `w-class="{ 'active': !!isActive }"` — добавляет CSS-классы по условию. Принимает объект где ключ это класс, значение — условие.
- `w-bind="keyPath"` — двустороннее связывание для `input`, `select`, `textarea`. Пользователь вводит — стейт обновляется автоматически.
- `w-value="exp"` — одностороннее: из стейта в элемент. Только для `input`, `select`, `textarea`.
- `w-disabled="!!exp"` — блокирует элемент. Работает на `input`, `select`, `textarea`, `button`.
- `w-checked="!!exp"` — управляет `checked` для `input[type=checkbox]` и `input[type=radio]`.
- `w-selected="!!exp"` — управляет `selected` для `select` > `option`.
- `w-src="exp"` — устанавливает `src` у картинки после вставки в DOM. Всегда используйте вместо обычного `src` когда путь динамический.
- `w-on="event:fn"` — привязывает обработчик объявленный через `.fn()`. Работает в паре с ним:
```html 
<button w-on="click:handleSubmit">Отправить</button>
```
```js 
$('#app')
  .state({})
  .fn('handleSubmit', state => function(e) {
      // обработчик
  })
  .mount()
```
- `w-static` — помечает блок как статический. Рендерится один раз и полностью выпадает из цикла перерисовки.
- `w-id="exp"` — присваивает виртуальному узлу стабильный идентификатор для точного патчинга при обновлениях.

# API

## Глобальные функции
После подключения CDN всё доступно через `window.vm`:
```js 
const { component, directive, filter, View, useJQuery } = window.jqvm
```
В проекте с модульной сборкой — через импорт:
```js 
import { component, directive, filter, View, useJQuery } from 'wex'
```
- `component(name, compile, affect)` — зарегистрировать компонент глобально. Доступен во всех шаблонах страницы.
- `directive(name, compile, affect)` — зарегистрировать директиву глобально.
- `filter(name, formatter)` — зарегистрировать фильтр глобально.
- `useJQuery(jQuery)` — передать свою версию jQuery если нужна не та что висит на `window.$`.
- `View` — конструктор вью. Нужен когда хотите проверить принадлежность объекта: `myView instanceof View`.

## Создание вью — $.fn.state
WEX — это jQuery-плагин. Точка входа всегда одна:
```js 
const view = $('#app').state(initState)
```
`.vm()` — полный алиас для `.state()`, работает идентично. 
WEX берёт HTML из выбранного элемента как шаблон и создаёт вью-объект. 
Рекомендуется использовать тег <template> — иначе браузер может отрендерить 
содержимое раньше чем WEX его обработает.

`initState` может быть объектом или функцией возвращающей объект:
```js 
// объект — один на все монтирования, делится между ними
$('#app').state({ title: 'Привет' })

// функция — каждый раз новый независимый объект
$('#app').state(function() {
    return { title: 'Привет' }
})
```
Функция важна когда вы монтируете и демонтируете вью несколько раз — каждый `.mount()` 
получит свежий стейт, а не общий с предыдущим:
```js 
const view = $('#app').state(function init() {
    return { count: 0 }
})

view.mount()
view.unmount()
view.mount() // count снова 0, не сохранился от прошлого монтирования
```
```
Передавать экземпляры классов (new Something()) нельзя — только простые объекты.
```

## Методы вью
Все методы возвращают `view` и поддерживают цепочку.

`.mount(el?)` — вставить вью в DOM. Без аргумента рендерится сразу после 
элемента-шаблона. С аргументом — монтируется внутрь указанного контейнера:
```js 
// после шаблона в DOM
view.mount()

// внутрь конкретного элемента
view.mount('#my-container')
view.mount($('#my-container'))

// или из строки шаблона
$('<template><div>{{title}}</div></template>')
  .vm({ title: 'Привет' })
  .mount('div#app')
```
- `.unmount()` — убрать из DOM, сохранив все подписки. После `unmount()` можно снова вызвать `mount()`.
- `.destroy()` — убрать из DOM и очистить все подписки. После `destroy()` можно монтировать снова, но обработчики нужно навесить заново.
- `.update(nextState?)` — обновить стейт и перерендерить:
```js 
view.update({ title: 'Новый заголовок' }) // смержит как React setState
view.update(true)                          // принудительный ре-рендер без изменений
view.update(state => {                     // функция — полный контроль
    state.count++
})
```
- `.find(selector)` — найти элемент внутри контейнера вью. Аналог `$.fn.find`:
```js 
const $button = view.find('.submit-btn')
```

## Обработчики событий
`.on(event, selector?, action)` — подписаться на событие. 
Главное отличие от jQuery: `action` — это функция которая возвращает другую функцию:
```js 
view.on('click', '.btn', function action(state, ...args) {
    const view = this // доступ к самому вью

    state.count++ // изменение стейта вызовет ре-рендер

    // возвращаем обработчик DOM-события — необязательно
    return function handle(e) {
        const $el = $(this)
        console.log('кликнули на', $el.text())
    }
})
```

Внешняя функция получает стейт и вызывается при каждом событии. 
Внутренняя — это обычный jQuery-обработчик с доступом к `e` и `this`. 
Если DOM-событие не нужно — внутреннюю функцию можно не возвращать.

Асинхронность работает без оговорок:
```js 
.on('click', '.load-btn', state => {
    setTimeout(() => state.items = ['один', 'два'], 1000)
    // через секунду — автоматический ре-рендер
})
``` 
Если изменили экземпляр класса или что-то нереактивное — вызывайте `update()` вручную:
```js 
.on('click', '.btn', state => {
    state.myChart.data = [1, 2, 3] // Chart.js не plain object
    this.update()                  // явный ре-рендер
})
``` 
- `.once(event, selector?, action)` — то же что `.on()` но сработает только один раз. Аналог jQuery `.one()`.
- `.off(event, selector?, action)` — отписаться от события навешенного через `.on()`.

## fn — именованные функции
- `.fn()` регистрирует функцию на вью по имени. Нужно для w-on директивы и для компонентных событий `@`:
```js 
$('#app')
  .state({ query: '' })
  .fn('handleSearch', state => function(e) {
      state.query = $(this).val()
  })
  .fn('handleClear', state => () => {
      state.query = ''
  })
  .mount()
```
```html 
<template id="app">
    <input w-on="input:handleSearch">
    <button w-on="click:handleClear">Очистить</button>
    <p>{{ query }}</p>
</template>
```
Получить функцию по имени — вызвать `.fn()` с одним аргументом:
```js 
const fn = view.fn('handleSearch') // вернёт функцию
``` 

## Внутренние события

Хуки жизненного цикла подписываются через тот же `.on()` — просто имя события начинается с `$`:
```js 
$('#app')
  .state({ data: [] })
  .on('$mount', state => {
      // вью появился в DOM — загружаем данные, AJAX-way подход
      $.get('/api/items').then(data => state.data = data) 
      
      // альтернативный современный подход, рекомендуется.
      $wire.get('/api/items').to(state.data);
  })
  .on('$unmount', state => {
      // вью убран — чистим за собой
  })
  .on('$change', state => {
      // стейт изменился
  })
  .on('$render', state => {
      // DOM перерисован
  })
  .mount()
``` 
  Событие  |        Когда
-----------+---------------------------
`$mount`   | После вставки в DOM
`$unmount` | После удаления из DOM
`$destroy` | После полного уничтожения
`$change`  | При изменении стейта
`$render`  | После каждого ре-рендера
