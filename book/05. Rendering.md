# Статические узлы

Реактивность — это удобно, но не бесплатно. При каждом изменении стейта 
WEX проходит по шаблону, сравнивает виртуальное дерево с реальным DOM 
и обновляет то, что изменилось. Для большинства элементов это быстро, 
но если в шаблоне есть блоки которые никогда не зависят от стейта — 
зачем тратить на них время при каждом перерендере?

Именно для этого существует `w-static`. Один раз отрисовал — и больше не трогаю.

```html 
<template id="app">
    <div w-static>
        <h1>Добро пожаловать в наш магазин</h1>
        <p>Работаем с 2010 года. Доставка по всей стране.</p>
    </div>

    <p>Товаров в корзине: {{ cartCount }}</p>
    <button class="add-btn">Добавить</button>
</template>

<script>
    $('#app')
      .state({ cartCount: 0 })
      .on('click', '.add-btn', state => {
          state.cartCount++;
      })
      .mount()
</script>
```

Заголовок и описание отрисуются один раз при монтировании. 
Сколько бы раз `cartCount` ни менялся — WEX не будет заходить в этот блок вообще.

## Когда w-static особенно полезен

Статичные шапки, футеры, иконки, рекламные баннеры, длинные текстовые блоки — 
всё что не меняется в зависимости от данных. Особенно заметный эффект даёт 
разметка со сложной структурой или большим количеством вложенных тегов:

```html 
<template id="app">
    <header w-static>
        <nav>
            <a href="/">Главная</a>
            <a href="/catalog">Каталог</a>
            <a href="/about">О нас</a>
            <a href="/contacts">Контакты</a>
        </nav>
    </header>

    <main>
        <p>Привет, {{ username }}!</p>
        <button class="logout-btn">Выйти</button>
    </main>

    <footer w-static>
        <p>© 2024 Все права защищены</p>
    </footer>
</template>

<script>
    $('#app')
      .state({ username: 'Алиса' })
      .on('click', '.logout-btn', state => {
          state.username = 'Гость';
      })
      .mount()
</script>
```

header и footer заморожены навсегда. При клике на кнопку обновится только 
`username` внутри main — WEX даже не посмотрит в сторону статичных блоков.

⚠ `w-static` — необратимо. После первого рендера блок отвязывается 
от реактивной системы полностью. Не используйте его там где 
данные могут измениться — даже если сейчас кажется что не изменятся.

# Как WEX работает под капотом

Когда вы пишете `.state({...}).mount()` — снаружи всё выглядит как магия. 
Данные меняются, страница обновляется сама. Но внутри происходит чёткая 
последовательность шагов, понимание которой помогает писать более осознанный 
код и объясняет почему одни вещи работают именно так, а не иначе.

## Реактивный стейт — прокси над объектом

Первое что делает WEX при монтировании — оборачивает ваш объект состояния в `Proxy`. 
Это стандартный JavaScript-механизм перехвата операций над объектом.
```html 
$('#app')
  .state({ count: 0 }) // ← этот объект станет Proxy
  .mount()
```

Каждый раз когда вы делаете `state.count = 5` внутри обработчика — `Proxy` перехватывает 
это присвоение и вызывает `nextTick`. Сам `nextTick` — это `throttle-функция` с задержкой 
16 миллисекунд (одного кадра). Это значит что если вы изменили стейт десять раз подряд 
в одном обработчике — перерисовка произойдёт один раз, по истечении 16мс. 
Никаких лишних перерисовок.

```js 
.on('click', '.btn', state => {
    state.a = 1  // ← Proxy поймал
    state.b = 2  // ← Proxy поймал
    state.c = 3  // ← Proxy поймал
    // перерисовка будет одна, через ~16мс
})
```

## Цикл рендеринга в 4 шага.

Каждый раз когда стейт изменился и пришло время обновить DOM, WEX запускает функцию `render`. 
Внутри неё происходят четыре фазы строго по порядку: `prepare` → `compile` → `diffAndPatch` → `affect`

### 1. prepare — сброс эффектов

Перед новым рендером WEX обходит все ранее зарегистрированные записи скомпилированных узлов 
и вызывает у каждого функцию `revoke` — если она есть. Это чистка побочных эффектов прошлого 
рендера: снятие обработчиков событий, отписки от наблюдателей.

Именно поэтому `w-bind` не накапливает бесконечные `input`-листенеры при каждом ре-рендере 
— каждый прошлый листенер аккуратно снимается перед новым рендером.

### 2. compile — виртуальное дерево

WEX берёт HTML-строку из вашего `<template>` и строит из неё новое дерево узлов — 
но не в реальный DOM, а в отдельный `<div>` в памяти. На этом этапе:
- обрабатываются все директивы (`w-for`, `w-if`, `w-class` и остальные)
- интерполируются все `{{ выражения }}`
- создаются или переиспользуются экземпляры дочерних компонентов

Результат — массив готовых DOM-узлов, которые пока ни к чему не подключены.

### 3. diffAndPatch — умное обновление

Вот здесь и живёт главная оптимизация. WEX не заменяет весь DOM — 
он сравнивает только что скомпилированное дерево с тем что уже стоит 
на странице, и точечно обновляет только то что изменилось.

Было в DOM:       Пришло новое:    Итог:
<li>Хлеб</li>     <li>Хлеб</li>    → не тронуто
<li>Молоко</li>   <li>Кефир</li>   → textContent обновлён
<li>Сыр</li>      (нет)            → удалён

При сравнении узлов WEX смотрит на `id`, `data-id` и `w-id` — именно поэтому 
`traceby` в `w-for` так важен. Без него фреймворк ориентируется только 
по позиции и типу тега, что менее точно.

### 4. affect — живые эффекты
После того как DOM обновлён, WEX проходит по всем скомпилированным 
записям ещё раз и запускает функции `affect` — это финальная фаза 
где директивы получают доступ к реальным DOM-элементам. 
Именно здесь `w-bind` вешает input-листенер, `w-src` ставит настоящий 
`src` на картинку, `w-on` регистрирует обработчик событий через `view.on`.

Разделение `compile` и `affect` сделано намеренно: на этапе компиляции 
элементы ещё не в DOM, события на них вешать бессмысленно.

## Как w-static выключается из этого цикла

Теперь понятно почему w-static такой эффективный. Заглянув в исходник 
можно увидеть что это вовсе не специальная директива — это компонент, 
который подписывается на внутреннее событие $update и немедленно вызывает prevent():
```js 
component(
  'w-static',
  () => $('<template><slot></slot></template>')
    .vm()
    .on('$update', () => (e, state, prevent) => {
      prevent()  // ← просто говорит "не надо меня перерисовывать"
    })
)
```

Первый рендер проходит нормально. При каждом последующем вызове `render` 
— компонент блокирует фазу `compile` для своего поддерева. 
До `diffAndPatch` дело просто не доходит.

## Вся картина целиком
```
   Изменился стейт
      ↓
   Proxy перехватил
      ↓
   nextTick (ждём 16мс, собираем все изменения)
      ↓
   render()
      ↓
   prepare()        — снимаем старые эффекты
      ↓
   compile()        — строим новое дерево в памяти
      ↓             ↑
      |             w-static → prevent() → стоп, этот узел пропускаем
      ↓
   diffAndPatch()   — сравниваем с реальным DOM, патчим точечно
      ↓
   affect()         — вешаем живые эффекты на реальные элементы
      ↓
   DOM обновлён.
```

Именно эта архитектура делает WEX предсказуемым: стейт — 
единственный источник правды, DOM — лишь его отражение. 
Вы никогда не трогаете DOM напрямую, а фреймворк сам разбирается 
что изменить, что оставить и что пропустить совсем.
